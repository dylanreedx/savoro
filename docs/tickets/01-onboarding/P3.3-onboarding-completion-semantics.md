# P3.3 — Make the server the authority for onboarding completion

Phase: 3 · Backend first-run profile
Track: backend
Execution: **autonomous**
Depends on: P3.2
Supersedes: OB-20

## Goal
`PATCH /v1/me/profile` transitions `onboardingState` per the approved contract so a reinstall can
ask `GET /v1/me` where to resume, with no client-side guessing.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. Verified today: `PATCH /v1/me/profile` lives at
`apps/api/src/routes/profiles.ts:23-28`, parses via `parseProfilePatch` (`:59-162`), and writes
through `updateUserProfile` (`apps/api/src/repo/profiles.ts:32-61`). `GET /v1/me`
(`routes/profiles.ts:18-21`) returns `mapMe`, which P3.1 extended with `onboardingState`. A fresh
user starts with `username: null` and `visibility: 'private'` (asserted in
`apps/api/test/profiles.test.ts:89-100`), and private/missing profiles share one 404
(`repo/profiles.ts:23-30`). The onboarding flow is: account created → username page → profile basics
→ done; the state derivation/transition rules come from the P0.8-approved contract, not from this
packet. This ticket is deliberately scoped so another fresh agent can verify and land it
independently.

## Approach
1. Read the approved `docs/api-contract.md` `onboardingState` section: exact states, what advances
them, and whether state is derived from columns or stored explicitly. Implement exactly that.
2. If the contract derives state from existing data (username present, profile step done), extend
the P3.1 derivation; if it stores state explicitly and P2.1's migration did not add the column, this
ticket is blocked — schema changes are not in this fence.
3. Wire the transition into the PATCH path: setting a username moves account-created → username-set;
completing profile basics (per the contract's definition of completion) moves username-set →
complete. Transitions are monotonic — a later profile edit never regresses a completed account.
4. Tests (in `apps/api/test/profiles.test.ts`), one per partial state, each asserting the `GET
/v1/me` view a reinstalled client would see:
   - fresh seeded account (no username) → earliest state;
   - after PATCH `{ username }` only → username-set state;
   - after the contract's completing PATCH → complete;
   - completing twice (repeat the same PATCH) → still complete, 200, idempotent — no error, no state
     regression;
   - a mid-onboarding account (username set, not complete) can keep `visibility: 'private'` and its
     profile stays publicly invisible: `GET /v1/profiles/:username` from another user returns 404.
5. Later profile edits (bio, links) after completion leave `onboardingState` at complete — add one assertion.

signup/login endpoints (P2.x) or seed tooling (P3.4).

## Done when
- Each transition the contract names is observable through `GET /v1/me` after the corresponding PATCH.
- Completing twice is idempotent (asserted).
- A mid-onboarding account is publicly invisible (404 via `/v1/profiles/:username` from a second
  user, asserted).
- No transition is reachable that skips the username page (a completing PATCH on an account with
  `username: null` must not yield complete — assert the contract's specified rejection or partial
  state).
- `bun run test && bun run typecheck` green.

## Watch out
- If the approved contract's transition rules require data this program hasn't landed (e.g. an
  explicit column P2.1 didn't create, or a signup-time marker from P2.3), mark blocked with the
  contract excerpt and the `src/db/schema.ts` evidence — do not improvise a derivation the contract
  doesn't define.
- "Complete" is defined by the contract, not by which fields happen to be non-null; do not infer
  completion from `displayName` presence unless the contract says so.
- Keep `parseProfilePatch` validation semantics untouched for existing fields; P3.2's availability
  logic is already the single username authority — reuse, don't fork.
- Idempotency means byte-identical success, not a swallowed error: the second completing PATCH
  returns 200 with the same state, and no `updatedAt` trickery hides a rejected write.
- The Apple signup path (`createSessionForAppleUser`, `apps/api/src/repo/sessions.ts:17-54`) creates
  users with `displayName: null` and no username — your earliest-state derivation must hold for BOTH
  auth methods' fresh accounts.
