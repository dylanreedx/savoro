# P8.4 — Verify Sign in with Apple on Dylan's physical iPhone against the deployed preview

Phase: 8 · Checkpoint A
Track: meta
Execution: **supervised**
Depends on: P8.3, P1.3
Supersedes: —

## Goal
Dylan proves on real hardware that the Apple Developer capability, entitlement, and deployed-preview exchange actually work — the one check no simulator can give.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. This is human gate 4 of 5 (`_DESIGN.md` §9):
"entitlements only prove themselves on Dylan's iPhone." Verified ground truth at program
authoring: the Apple Developer team `46TTB6J9DZ` is persisted in
`SavoroIOS/Savoro.xcodeproj/project.pbxproj` (commit `8c0fb27`), bundle id `com.savoro.Savoro`,
and **no `.entitlements` file or Sign in with Apple capability exists anywhere in the project
yet** — the simulator work ran through the P4.2 DEBUG mock adapter, which never exercises
entitlements. Server-side, `POST /v1/auth/apple` verifies real Apple tokens (JWKS, aud, iss, exp —
proven in P2.7) and P1.3 smoked the deployed preview Worker. This ticket is deliberately scoped so
another fresh agent can verify and land it independently — its code-free deliverable is a recorded
outcome.

## Files
- `docs/tickets/01-onboarding/_LEDGER.md` (verdict row, orchestrator-edited)
- new blocker packets under `docs/tickets/01-onboarding/` if any step fails

This fence is record-keeping; any capability/entitlement/code fix a failure reveals becomes its
own packet rather than ad-hoc edits during a supervised gate.

## Approach
1. The loop stops when this row is first eligible; the orchestrator presents Dylan this checklist
   and the exact preview base URL from P1.3.
2. Dylan confirms in the Apple Developer portal / Xcode Signing & Capabilities:
   - the App ID `com.savoro.Savoro` exists under team `46TTB6J9DZ` with the **Sign in with
     Apple** capability enabled;
   - the Savoro target carries the Sign in with Apple entitlement (if the P4/P5 tickets landed it,
     verify it; if not, this gate adds it via Xcode — the one sanctioned in-gate change, committed
     by Dylan);
   - automatic signing resolves with no errors.
3. Build and run a Debug (or preview-pointed) configuration on Dylan's physical iPhone with the
   base URL set to the deployed preview.
4. Dylan signs in with his real Apple ID: real `ASAuthorizationController` sheet → credential →
   `POST /v1/auth/apple` on the preview Worker → session stored in Keychain → onboarding username
   page reached (fresh account) or authenticated Today (existing account).
5. Relaunch the app: the Keychain session restores without re-auth.
6. Record device model, iOS version, app version/build, preview URL, and outcome per step in the
   ledger.

## Done when
- Sign in with Apple completes on a physical iPhone against the deployed preview and lands in the
  correct post-auth state, verified by Dylan's own eyes.
- Relaunch restores the session from Keychain.
- The `_LEDGER.md` row records device, iOS version, build, preview URL, per-step outcomes, and
  Dylan's explicit sign-off.
- Any failure: this row goes **blocked**, P8.5 stays closed, and each failure is captured as a new
  packet with the exact error (Xcode signing output, HTTP status, or console log).

## Verify
```bash
# entitlement present in the built product (run after the archive/build):
codesign -d --entitlements - <path-to-built .app> | grep -i applesignin
curl -s <preview-base-url>/health
```
Record in `_LEDGER.md`: the codesign entitlement output, the health-check response, device/iOS/
build identifiers, and the step-by-step outcome with Dylan's verdict verbatim.

## Watch out
- No entitlement file exists at program authoring — if P4.2/P5.1 never added one, the DEBUG mock
  adapter has been masking this the whole time; expect this gate to surface it. Adding the
  capability is Dylan's account action, not a worker's.
- Release never carries dev tokens (locked decision 11): the device build must authenticate
  through the real flow, not `SAVORO_API_TOKEN` injection — that seam is Debug-only and dies with
  P4.6 anyway.
- Sign in with Apple on device requires the Apple ID signed into iCloud on the phone; a failure
  there is environmental, not a code blocker — record it as such.
- Do not point the device at the local Worker (`127.0.0.1` is meaningless on-device); the deployed
  preview from P1.3 is the target.
- The loop never marks this row done on Dylan's behalf; any failure blocks P8.5 and becomes a
  ticket — no "worked after a retry" hand-waving without the failure recorded first.
