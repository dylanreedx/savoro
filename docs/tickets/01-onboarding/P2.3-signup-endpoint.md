# P2.3 — Implement POST /v1/auth/signup

Phase: 2 · Backend auth
Track: backend
Execution: **autonomous**
Depends on: P2.2
Supersedes: OB-13

## Goal
Land email/password signup per the approved contract: validate and normalize the email, reject duplicates with 409, create the user, and issue the same opaque session the Apple exchange issues.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. The Apple exchange is the template: `apps/api/src/routes/auth.ts` (`auth.post('/apple', …)`, lines 10–30) calls `createSessionForAppleUser` (`src/repo/sessions.ts`, lines 17–54), which returns the exact envelope `{ sessionToken, user: { id, email, displayName } }` (lines 50–53) with a 64-hex-char token generated by `generateSessionToken` (lines 56–60) and stored only as a SHA-256 hash. Locked decision 1: both auth methods converge on this same opaque session — reuse the issuance path, do not fork it. One gap to close: `ErrorCode` (`src/errors.ts`, line 4) is `'unauthorized' | 'not_found' | 'validation_failed' | 'internal'` — there is no 409 code yet; add `'conflict'` mapped to 409 in the `STATUS` table. This ticket is deliberately scoped so another fresh agent can verify and land it independently.

## Files
- `apps/api/src/routes/auth.ts`
- `apps/api/src/repo/sessions.ts` (extract shared session issuance; add the email-user creation)
- `apps/api/src/errors.ts` (`conflict` code only)
- `apps/api/test/auth-signup.test.ts` (new)

Signup only; login (P2.4), logout (P2.5), and any `GET /v1/me` shape work belong to their own tickets.

## Approach
1. Read the approved contract in `docs/api-contract.md` (P0.8) for the signup request body, password policy (the 422 "weak password" threshold), and response envelope. The envelope mirrors POST /v1/auth/apple — verify the contract agrees with the shape at `src/repo/sessions.ts` lines 50–53.
2. Refactor minimally: extract the session-insert block of `createSessionForAppleUser` (token generation, hashing, `sessions` insert, envelope assembly — lines 38–53) into a shared helper, e.g. `issueSession(db, user)`, and have BOTH the Apple path and signup call it. Behavior of the Apple path must not change — `test/auth-apple.test.ts` stays green untouched.
3. Add `createUserWithPassword(db, { email, passwordFields })` in `repo/sessions.ts` (or a sibling repo module): normalize email (trim + lowercase per contract), check for an existing row on the normalized value, insert with `hashPassword` output from `src/lib/passwords.ts` into the P2.1 columns.
4. Route `auth.post('/signup', …)`: parse/validate body (email format + password policy → `validation_failed` 422, matching the existing style at `routes/auth.ts` lines 11–14), duplicate email → `ApiError('conflict', …)` 409, success → `issueSession` envelope. Signup is unauthenticated — it must NOT sit behind `requireAuth`.
5. Tests in `test/auth-signup.test.ts` (mirror `test/auth-apple.test.ts` structure):
   - success: 200, envelope matches the Apple exchange shape, token matches `/^[0-9a-f]{64}$/`, DB row has normalized email and a password hash that is not the plaintext;
   - duplicate email → 409 `conflict` (also: same email with different case → 409, proving normalization);
   - invalid email → 422 `validation_failed`;
   - weak password (per contract policy) → 422;
   - the issued session works against the middleware: authenticated `GET /v1/logs/day?date=2026-06-10` returns 200 (same probe as `test/auth.test.ts`).

## Watch out
- Reuse, don't fork: if signup hand-rolls its own token/insert/envelope instead of sharing the Apple path's, that is rework — locked decision 1 exists precisely to prevent drift.
- No password reset or email verification surfaces (locked decision 2) — no "verify your email" fields, no reset stubs.
- The password policy comes from the approved contract, not from this packet; if `docs/api-contract.md` lacks a signup section, P0.8 did not land what this ticket needs — mark blocked with the contract's current state.
- Watch the duplicate check for the Apple-created users that already hold that email (`email` is unique, nullable — schema.ts line 8); the contract governs whether that is a 409 or an account-link flow. If it is silent, 409 and flag the question in your report.
- Do not touch `middleware/auth.ts` or session validation — expiry/revocation work is P2.5/P2.6.
