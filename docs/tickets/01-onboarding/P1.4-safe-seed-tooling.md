# P1.4 — Build remote-safe seed tooling for the preview database

Phase: 1 · Preview infrastructure
Track: backend
Execution: **autonomous**
Depends on: P1.3
Supersedes: OB-9

## Goal
Provide a seed path for the preview database that generates throwaway credentials, prints them exactly once, and can never leak a fixed token — doubling as the manual account-recovery path while password reset does not exist.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. Today `apps/api/seed/` contains exactly three files: `local-dev.sql` (deterministic local fixture whose header, line 3, names the fixed bearer token `dev-alice-token`, with its SHA-256 hash inlined at line 16), `foods-fixture.sql` (12 test foods), and `import-usda.ts` (offline SQL generator). `local-dev.sql` is banned from remote use by `_DESIGN.md` decision 16. Sessions store only SHA-256 token hashes (`apps/api/src/token.ts` `hashToken`; enforced in `src/repo/sessions.ts` and asserted by `test/auth-apple.test.ts`). `_DESIGN.md` decision 2: no password reset at MVP — lockout recovery is manual re-issue via this tooling. This ticket is deliberately scoped so another fresh agent can verify and land it independently.

## Files
- `apps/api/seed/seed-preview.ts` (new)
- `apps/api/package.json` (one script entry)
- `docs/deploy-runbook.md` (usage + recovery section)
- `apps/api/test/seed-preview.test.ts` (new, if the SQL-generation core is factored testably; otherwise document why)

Fence covers the new tool and its docs only; do not touch `local-dev.sql`, `import-usda.ts`, or any `src/` runtime code.

## Approach
1. Write `apps/api/seed/seed-preview.ts` (run via `bun run seed/seed-preview.ts`). Two modes:
   - **create**: generate a fresh user id (`usr_<uuid>`) and a random 32-byte hex session token (same shape as `generateSessionToken` in `src/repo/sessions.ts`, lines 56–60), hash it with the same SHA-256 hex scheme as `src/token.ts`, and emit INSERTs for `users` + `sessions` matching the current schema (`src/db/schema.ts`: users lines 4–27, sessions lines 29–43 — `token_hash`, `expires_at`, `created_at` are NOT NULL).
   - **recover --user-id <id>** (or `--email`): mint a fresh session row for an existing user — the manual lockout-recovery path.
2. Apply the SQL via `wrangler d1 execute DB --env preview --remote --command "<sql>"` (or a temp file in the OS tempdir, deleted afterward). Never write generated SQL or tokens into the repo tree.
3. Print the plaintext token exactly once, to stdout, with a banner stating it will not be shown again and must not be committed or pasted into tracked files.
4. Refuse fixed inputs: the tool always randomizes tokens; there is no flag to supply one. Hard-fail if asked to target the local binding without `--local` intent being explicit, and hard-fail if any generated statement references `dev-alice-token` or `usr_dev_alice` (defense in depth).
5. Add a package script, e.g. `"seed:preview": "bun run seed/seed-preview.ts"`, and document create + recover usage in `docs/deploy-runbook.md`, cross-referencing the no-reset limitation.
6. If the SQL/token generation is factored as pure functions, unit-test them: token is 64 hex chars and unique across calls, stored value is the hash (never the plaintext), generated SQL contains the hash but not the token.

### Implementation sketch
```ts
// seed/seed-preview.ts (shape, not final code)
// bun run seed/seed-preview.ts create
// bun run seed/seed-preview.ts recover --user-id usr_...
const token = randomHexToken(32)           // same shape as generateSessionToken
const tokenHash = await sha256Hex(token)   // same scheme as src/token.ts
const sql = buildInserts({ userId, tokenHash, expiresAt: in30Days() })  // pure, testable
await applyRemote(sql)                     // wrangler d1 execute DB --env preview --remote
console.log(`ONE-TIME token for ${userId}: ${token}`)
console.log('This will not be shown again. Do not commit or paste into tracked files.')
```

## Done when
- Running the tool against preview creates a user + session; a curl to `GET /v1/logs/day?date=2026-06-10` on the preview URL with the printed token returns 200.
- The recover mode issues a working session for an existing user id.
- The plaintext token appears only in the one-time stdout output — never in any file under the repo, never in `_LEDGER.md` evidence (record user id + "token verified live" instead).
- No fixed or caller-supplied token is possible; grep of the tool shows no literal token values.
- Required negative witness: run the tool, then grep the working tree (`git status --porcelain` clean; `grep -r <printed-token-prefix> .` finds nothing) — record that both come back empty.
- `bun run test && bun run typecheck` pass.

## Verify
```bash
cd apps/api
bun run seed:preview            # capture printed user id; token stays in the terminal
curl -si 'https://<preview-url>/v1/logs/day?date=2026-06-10' -H "Authorization: Bearer <printed-token>"
git status --porcelain
bun run test && bun run typecheck
```
Record in `_LEDGER.md`: the created user id, the 200 transcript with the token REDACTED, the clean `git status`, and derived test counts.

## Watch out
- Never apply `seed/local-dev.sql` remotely, and never copy its pattern of a comment naming the token — the whole point of this tool is that no durable artifact carries the credential.
- `expires_at` filtering is live in `findUserIdByToken` (`src/repo/sessions.ts` line 11) — seed sessions with a sane future expiry (the existing convention is ISO-8601 UTC strings), not a past one.
- Schema drift: P2.1 adds password columns later; generate column-explicit INSERTs so this tool keeps working.
- The tool touches a real remote database — no destructive statements (no DELETE/DROP), inserts only.
- If preview is unreachable or unprovisioned, mark blocked citing the P1.2/P1.3 ledger rows; do not "test" the tool by running it against local and calling it done — the remote path is the deliverable.
