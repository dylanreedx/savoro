# P4.5 — Replace the unconditional tab boot with a root state machine

Phase: 4 · iOS auth core
Track: frontend
Execution: **autonomous**
Depends on: P4.4, P4.2
Supersedes: OB-26

## Goal
`SavoroApp` owns an explicit `signedOut → onboarding(step) → authenticated` root state driven by
SessionStore restore and `GET /v1/me`'s `onboardingState`, and no tab bar renders before
authenticated.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. Verified today: `SavoroApp`
(`SavoroIOS/Savoro/App/SavoroApp.swift:1-12`) boots straight into
`RootPlaceholderView(environment:)` with no gate of any kind; `RootPlaceholderView`
(`App/RootPlaceholderView.swift:241-267`) wraps `SavoroTabShellView`, whose `TabView` (`:308`)
renders all 5 tabs via the switch at `:382-408` (today/cookbook/discover/community/profile). There
is no auth, onboarding, or session concept anywhere in `App/`. Available from dependencies:
`SessionStore` (P4.1), `AppleAuthorizing` (P4.2), `CurrentUserRequest`/`CurrentUser.onboardingState`
(P4.3), and the central 401 hook on `URLSessionAPIClient` (P4.4). This ticket lands the STATE
MACHINE and routing shell; the actual onboarding screens are P5.x — mid-onboarding states may route
to plain placeholders. This ticket is deliberately scoped so another fresh agent can verify and land
it independently.

## Approach
1. Create `App/RootStateMachine.swift` (or `Core/Auth/` if cohesion is better — pick one, say why in
the report): an `@Observable`/testable reducer with state `enum RootState: Equatable { case
launching; case signedOut; case onboarding(OnboardingStep); case authenticated }` where
`OnboardingStep` maps 1:1 from the contract's `onboardingState` cases. Inputs (events):
launch-restore result, `GET /v1/me` result, sign-in success, onboarding-step completion, sign-out,
and mid-session 401.
2. Launch flow: restore token via `SessionStore` → nil token ⇒ `signedOut`; token present ⇒ fetch
`/v1/me` ⇒ `onboardingState` complete ⇒ `authenticated`, otherwise `onboarding(step)` per the server
value (server-authoritative resume, locked design §4); `/v1/me` 401 ⇒ clear session ⇒ `signedOut`.
3. Wire P4.4's `onUnauthorized` hook so a mid-session 401 anywhere drives the machine to `signedOut`
(session already cleared by the hook).
4. In `SavoroApp.swift`, switch on the root state: `authenticated` renders the existing
`RootPlaceholderView`; `signedOut`/`onboarding` render minimal placeholder views (real screens are
P5.x — keep copy calm, no banned words, no "mock"); `launching` renders a neutral launch view.
5. Keep the machine pure/injectable (protocol-typed session store + me-fetching closure) so every
transition is a unit test with no networking.
6. Tests (`SavoroTests/RootStateMachineTests.swift`) — one per transition:
   - fresh install (no token) → `signedOut`;
   - token + `/v1/me` complete → `authenticated`;
   - token + each mid-onboarding `onboardingState` → the matching `onboarding(step)` (resume-after-reinstall);
   - token + 401 on launch → `signedOut`;
   - mid-session 401 event from `authenticated` → `signedOut`;
   - sign-in success from `signedOut` → onboarding or authenticated per the returned state;
   - sign-out from `authenticated` → `signedOut` with session cleared;
   - no-tab-bar guard: assert the view for every non-`authenticated` state does not build
     `SavoroTabShellView` (type-level assertion on the root view builder, or a view-model-level
     `showsTabs` flag asserted false).

AppEnvironment/Release config (P4.6), or Today's fixture cleanup (P8.2).

## Done when
- Every transition above has a named passing unit test, including 401 mid-session → `signedOut`.
- The tab shell is unreachable in `signedOut`/`onboarding`/`launching` (asserted, not eyeballed).
- Resume is server-authoritative: the step comes only from `/v1/me`'s `onboardingState`, never from
  local persistence.
- Existing suite still green (snapshot tests of tab content must not regress — the authenticated
  path renders the same `RootPlaceholderView`).
- Placeholder copy passes the banned-copy rules (`_RUNBOOK.md`).

## Watch out
- If P4.3's landed `onboardingState` cases differ from what this packet assumed, map 1:1 to the
  landed enum; if the landed contract has no state usable for resume, mark blocked with the contract
  excerpt.
- `SavoroTabShellView` seeds fixture state (`dayLog: .todayFixture` etc.,
  `RootPlaceholderView.swift:281-283`) — leave that untouched; fixture removal is P8.2's fence.
- Don't store the onboarding step in UserDefaults "for offline" — reinstall-resume must come from
  the server (locked decision, `_DESIGN.md` §4).
- Snapshot suites instantiate `RootPlaceholderView()` directly (e.g. previews at `:777-780`); keep
  its initializer compatible.
- Beware `@MainActor`/`Sendable` friction between the 401 hook (background) and the observable state
  — hop explicitly, no `DispatchQueue.main.async` fire-and-forget in the reducer itself.
