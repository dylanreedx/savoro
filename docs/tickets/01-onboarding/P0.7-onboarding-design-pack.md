# P0.7 — Author the onboarding design pack

Phase: 0 · Foundations and contracts
Track: frontend
Execution: **autonomous**
Depends on: P0.1
Supersedes: OB-4, OB-5, OB-6 (docs/epics/onboarding.md)

## Goal
A reviewable design pack — one spec doc plus low-fi wireframes — covering every onboarding surface
and the goal-less Today, so Dylan can approve or redline the whole flow in one sitting at P0.8.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. This resolves backlog item R-4
(`docs/backlog-local.md` lines 241–245: first-run flow, Sign in with Apple, initial goal setup, and
any goal-editing surface are missing from the prototype entirely). The locked decisions in
`_DESIGN.md` §2 are instructions: username on its own page for BOTH auth methods (item 4); targets
calories-first with a derived editable P/C/F split and first-class Skip (items 6–7); intent as a
client-side routing hint with three options (item 8); goal-less Today with bare totals, no ring
denominator, no progress copy (item 7); privacy defaults to `private` (item 14). Copy is drafted in
the product voice — calm, non-judgmental — and the banned list in `_RUNBOOK.md` (adherence,
compliance, failure, failed, over limit, guilt, cheat, bad food, raw IDs, `mock`, `scaffold`,
backend jargon) applies to every drafted string. This ticket is deliberately scoped so another fresh
agent can verify and land it independently.

## Files

## Approach
1. Choose the wireframe medium and state it: ASCII layout blocks embedded in the spec, or PNGs
   rendered from throwaway SwiftUI previews. If PNGs, they are committed under `design/` and no
   preview code lands in the app target.
2. Spec each screen, one section apiece, in this order (the flow order):
   1. welcome/auth (Apple button + email entry),
   2. email credential forms (signup + login, inline validation),
   3. username page (availability, suggestions, rules copy — both auth methods arrive here),
   4. profile basics (optional display name + private-by-default explainer),
   5. intent page (exactly 3 options: "Track what I eat" / "Build my recipe collection" / "Both"),
   6. targets page (calories-first entry, derived editable P/C/F split, prominent guilt-free Skip),
   7. goal-less Today state (bare totals, one calm add-targets affordance),
   8. Profile account screen (view/edit targets, account info, sign out).
3. For every screen, spec all three named states — normal, loading, error — with a wireframe and the
   exact behavior of each (what is disabled, what the error surface looks like, how retry works).
4. Draft the actual copy for every visible string (titles, field labels, helper text, error
   messages, buttons) in the product voice; run the drafted strings against the banned list before
   finishing.
5. Note per screen which `_DESIGN.md` decision(s) it embodies and which queue ticket builds it
   (P5.1–P5.6, P6.2, P6.3), so redlines map cleanly to tickets.
6. Keep it low-fi and reviewable in one sitting: layout, hierarchy, states, and copy — not pixel
   values. New screens will compose L-35 design-system primitives; the spec should reference
   primitives, not invent new ones.

## Done when
- Every one of the 8 named screens has: a wireframe, all three states (normal/loading/error) speced,
  and drafted copy for every visible string.
- Drafted copy contains no banned term (self-check documented in the spec).
- The intent page has exactly 3 options and is marked client-side only; the targets page's Skip is
  prominent and judgment-free; the goal-less Today shows no denominator, ring math, or progress
  copy.
- The pack is a single entry point (`onboarding-design-spec.md`) Dylan can review in one sitting,
  with each screen traceable to its implementing ticket.
- Nothing outside `docs/tickets/01-onboarding/design/` changed.

The grep must return only intentional mentions (e.g. the banned-list self-check section), never a
drafted string. Record in `_LEDGER.md`: the file list, the grep result, and confirmation the tree
shows only `design/` additions.

## Watch out
- This is design, not implementation: no Swift files, no snapshot references, no Xcode project
  changes. PNGs (if chosen) come from throwaway previews that are not committed.
- Do not design password reset, email verification, micronutrients, or coached goal math — explicit
  non-goals (`_DESIGN.md` §8).
- Do not soften Skip into a dark pattern or an apology; it is a designed first-class mode
  (`_DESIGN.md` §1).
- Copy that names raw IDs, jargon, or any banned term is a blocker, not a draft note.
- If a locked `_DESIGN.md` decision cannot be honored on a screen (e.g. the 3-option intent
  conflicts with a landing-tab constraint you discover), mark the ticket blocked with the concrete
  conflict rather than improvising a fourth option.
