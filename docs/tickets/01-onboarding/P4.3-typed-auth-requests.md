# P4.3 — Add typed auth requests and a nullable-identity CurrentUser decode

Phase: 4 · iOS auth core
Track: frontend
Execution: **autonomous**
Depends on: P4.1, P3.1
Supersedes: OB-24 (and the mid-onboarding decode fix)

## Goal
Typed requests for signup, login, logout, the Apple exchange, and `GET /v1/me` decode the approved
envelopes — including the mid-onboarding payload where `username` is null.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. CRITICAL verified fact:
`SavoroIOS/Savoro/Core/Models/SocialModels.swift:14` declares `let username: String` (non-optional)
on `UserProfile`, while the backend emits `username: null` for every mid-onboarding account — the
first live `GET /v1/me` decode for a fresh user throws. Direction: add a NEW `CurrentUser` DTO for
the me-envelope (nullable identity + `onboardingState` per the P3.1-landed contract) and leave the
public-profile `UserProfile` non-optional — public profiles only exist post-onboarding. Also
verified: `NutritionModels.swift:302-351` `Goal` hard-decodes `dailyTargets` at line 337 — do NOT
route `/v1/me` decoding through `Goal` or any nutrition type. The Apple exchange envelope is `{
sessionToken, user: { id, email, displayName } }` (`apps/api/src/repo/sessions.ts:50-53`);
signup/login envelopes come from the P0.5-approved contract. Request-type precedent:
`Core/API/LoggingRequests.swift` (`APIRequest` structs, `JSONEncoder.savoro`). This ticket is
deliberately scoped so another fresh agent can verify and land it independently.

## Approach
1. Create `Core/Auth/AuthRequests.swift` with `APIRequest`-conforming types (pattern per
`LoggingRequests.swift`): `AppleAuthExchangeRequest` (`POST /v1/auth/apple`), `SignupRequest`,
`LoginRequest`, `LogoutRequest` — paths, bodies, and response envelopes byte-exact to the approved
contract sections (read them from `docs/api-contract.md` first). Shared response type for the
session envelope since both methods return the same shape (locked decision 1).
2. Create `Core/Auth/CurrentUser.swift`: a `CurrentUser` DTO (naming per approved contract) modeling
the `GET /v1/me` envelope — nullable `username`/`displayName` (exactly the fields the contract makes
nullable mid-onboarding), `onboardingState` as an enum with the contract's cases, and NO fallback of
any kind: a missing username decodes as nil, never as a user id or placeholder (locked decision 5).
Add `CurrentUserRequest` (`GET /v1/me`).
3. Decode with `JSONDecoder.savoro` (defined in `Core/Fixtures/FixtureLoader.swift:35`) — confirm
its date strategy matches the me-envelope's timestamps before relying on it.
4. Keep `UserProfile` (`SocialModels.swift:12-25`) untouched.
5. Tests (`SavoroTests/AuthRequestTests.swift`), mirroring the contract-exact style of
`ScaffoldTests.testLiveTodayRequestsUseV1PathsAndContractExactBodies`
(`ScaffoldTests.swift:2205-2229`):
   - request shape: each auth request's path/method/body keys are contract-exact (assert key sets like
     `:2225`);
   - decode fixtures for EVERY `onboardingState` case, including a fresh-account fixture with
     `"username": null` — assert nil, not a crash, not a substitute string;
   - session envelope decode for the Apple exchange and email login;
   - a fixture with an unknown `onboardingState` value behaves per contract (fail loudly or
     forward-compatible case — whichever the contract specifies; assert it).

## Watch out
- If the P0.5/P0.4-approved contract envelopes differ from the current compiled backend
  (`repo/sessions.ts` shape, P3.1's landed `mapMe`), the CONTRACT wins for request shapes — but if
  contract and landed backend disagree with each other, mark blocked with both excerpts; do not
  split the difference.
- No raw-ID fallback and no placeholder strings ("New user", "user") in the DTO layer — display
  fallbacks are a UI decision for P5.x under the design pack.
- Signup/login bodies must never log or embed passwords in errors; keep payload types out of
  `debugDescription`.
- `JSONDecoder()` default date decoding will not match ISO-8601 strings; use `.savoro` and verify
  against a real timestamp fixture.
- Do not "conveniently" add the availability-check request here if the contract defines one — that
  ships with the username page ticket that consumes it.
