# P5.2 — Build the email signup and login forms

Phase: 5 · Onboarding UI
Track: frontend
Execution: **autonomous**
Depends on: P5.1, P2.4
Supersedes: OB-29

## Goal
Ship signup and login forms — email + password with inline validation and calm error states — that
exchange credentials for a session via the P4.3 typed requests.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. P5.1's `emailEntry-handoff` state routes here.
The backend endpoints are P2.3/P2.4 (`POST /v1/auth/signup`, `POST /v1/auth/login`, per the
P0.5-approved contract): 409 duplicate email, 401 bad credentials (deliberately indistinguishable
from unknown email), 422 weak password. There is NO password reset or email verification at MVP
(locked decision 2) — the forms must not promise either. Both methods issue the same opaque session;
after exchange, hand off to the P4.5 state machine exactly as the Apple path does. All P5 screens
build ONLY after the P0.8 design verdict and must match the approved design pack in
docs/tickets/01-onboarding/design/. This ticket is deliberately scoped so another fresh agent can
verify and land it independently.

## Files
- `SavoroIOS/Savoro/Features/Onboarding/EmailCredentialsView.swift` (new — signup + login forms and
  view model)
- `SavoroIOS/SavoroTests/OnboardingTests.swift` (extend — validation, error mapping, copy)
- `SavoroIOS/SavoroTests/SnapshotTests.swift` (add credential-form snapshot cases)
- `SavoroIOS/Scripts/record-snapshots.sh` (bump `expected_snapshot_count`)

This fence is the credential UI plus its evidence; do not absorb adjacent work (no username page —
P5.3; no changes to P4.3 request types or the API client).

## Approach
1. One view with a signup/login mode toggle (or two thin views over one view model — follow the
   approved design pack), email field + `SecureField` password entry, built from L-35 primitives.
2. Inline client-side validation before submit: plausible email shape, non-empty password;
   validation messages are guidance, never scolding.
3. Submit through the P4.3 typed signup/login requests; on success pass the session to the P4.5
   state machine (which persists via P4.1 SessionStore and advances to the username step).
4. Map the server error taxonomy to human copy in one testable function, e.g. 409 → "That email
   already has a Savoro account — try signing in instead", 401 → "That email and password don't
   match what we have", 422 → "Choose a longer password to keep your account safe". Exact words per
   the design pack; the banned-copy list is the hard constraint.
5. Named UI states: signup-idle, login-idle, inline-validation, submitting, server-error.
6. Unit tests: error-code → copy mapping for 409/401/422 (assert none contain banned terms,
   especially "failed"); inline validation; submitting disables the button.
7. Snapshot every named state across the full matrix.

## Done when
- Signup and login both reach an authenticated session against the mocked P4.3 layer in tests; the
  state machine hand-off is asserted.
- 409/401/422 each render distinct, calm, human copy; a unit test pins all three strings and proves
  them banned-copy-clean.
- Snapshot matrix {light,dark} × {standard,XXXL} exists for every named state (signup-idle,
  login-idle, inline-validation, submitting, server-error).
- No password-reset or verification affordance appears anywhere.
- Full iOS suite green with the grown snapshot count.

## Watch out
- Banned copy list applies (no failure/failed/guilt/etc.) — the 401/422 messages are where
  "failed"/"invalid"/"weak" shame-copy sneaks in; the server's own `validation_failed` code must
  never surface verbatim.
- Build from L-35 design-system primitives; no raw padding/colors/fonts.
- Do not echo raw error envelopes, codes, or backend jargon in visible strings; map at one seam and
  test that seam.
- Snapshot reference counts in `Scripts/record-snapshots.sh` grow deliberately in this ticket only.
- Verify the real signup/login route behavior in `apps/api/src/routes/auth.ts` as landed by
  P2.3/P2.4 before pinning copy to status codes; if the taxonomy differs from 409/401/422, follow
  the code and note the delta. If it conflicts with the approved contract, mark blocked with
  evidence.
