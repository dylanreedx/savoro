# P3.2 — Ship the username availability check

Phase: 3 · Backend first-run profile
Track: backend
Execution: **autonomous**
Depends on: P3.1
Supersedes: OB-19

## Goal
The signup username page has a server check it can call per keystroke-debounce: available, taken,
invalid, or reserved — in whichever shape the approved contract chose.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. The approved P0.4 contract (landed at P0.8)
decided between a dedicated GET availability route and a documented 422-probe of `PATCH
/v1/me/profile`; implement exactly the landed choice — check `git log --oneline
docs/api-contract.md` for the `[Contract]` commit and read that section before writing code.
Verified today: the username regex lives at `apps/api/src/routes/profiles.ts:72` and is
`/^[a-z0-9](?:[a-z0-9_-]{1,28}[a-z0-9])$/`; uniqueness is enforced by `assertUsernameAvailable` at
`apps/api/src/repo/profiles.ts:63-71` (throws `validation_failed`, "Username is already in use.").
CORRECTION to OB-19's wording: **no username denylist exists anywhere in `apps/api` today** — only
the regex and the uniqueness check. This ticket is deliberately scoped so another fresh agent can
verify and land it independently.

## Files
- `apps/api/src/routes/profiles.ts`
- `apps/api/src/repo/profiles.ts`
- `apps/api/src/dto/profiles.ts` (only if the contract defines a response DTO)

This fence is the existing profile route/repo/test surface the check reuses; do not absorb

## Approach
1. Read the approved contract section. Two possibilities:
   - **GET availability route** (e.g. `GET /v1/me/username-availability?username=…` or similar — use
     the contract's exact path and response shape): add it to the `me` router in `routes/profiles.ts`
     (it already applies `requireAuth` via `me.use('*', requireAuth)` at line 15).
   - **Documented 422-probe**: no new route; instead land tests that pin the probe behavior of `PATCH
     /v1/me/profile` (422 + stable error code for taken/invalid/reserved, 200 for available) so the iOS
     page can rely on it.
2. Extract the regex from `parseProfilePatch` (`routes/profiles.ts:67-79`) into one shared constant
so the check and the PATCH validation cannot drift; reuse `assertUsernameAvailable` (export it or
add a non-throwing `isUsernameTaken` beside it in `repo/profiles.ts`) rather than duplicating the
query.
3. Denylist: if the approved contract defines reserved usernames, implement that exact list as a
module constant checked in the same place as the regex, and wire it into BOTH the availability check
and `parseProfilePatch` (a name must not be "available" yet rejected on submit, or vice versa). If
the approved contract defines no denylist, implement none — adding one would be a contract change,
which is human-only — and record that in the ledger note.
4. Tests in `profiles.test.ts`: available name; name taken by another user; own current username
(should read as available/no-op per contract); invalid syntax (uppercase, 2 chars, leading hyphen —
mirror the invalid set at lines 137-149); denylisted name (only if step 3 applies); unauthenticated
request → 401.

## Done when
- The contract-chosen mechanism exists and matches the approved shape byte-for-byte (path,
  query/body params, response envelope, error codes).
- Regex and uniqueness logic are shared with `PATCH /v1/me/profile`, not copied.
- Tests cover: available, taken, invalid syntax, denylisted (or a ledger note that the approved
  contract defines no denylist), plus 401.
- A name reported available can immediately be claimed via `PATCH /v1/me/profile`, and a name
  reported taken is rejected by it — asserted in one round-trip test.
- `bun run test && bun run typecheck` green.

## Watch out
- If the approved contract section is absent from `docs/api-contract.md` or ambiguous about the
  mechanism, mark this ticket blocked quoting the contract text — do not pick a shape yourself.
- OB-19 claims an "existing denylist"; the repo has none (verified 2026-08-02). If the packet's
  assumption and compiled reality conflict beyond this, prefer the repo and say so in your report.
- The availability check must not leak whether a PRIVATE profile owns a name differently than a
  public one — "taken" is "taken", one response shape.
- Keep the check read-only: it must never reserve, hold, or mutate anything.
- Do not weaken `parseProfilePatch` validation to make the check simpler; the PATCH remains the
  single write-path authority.
