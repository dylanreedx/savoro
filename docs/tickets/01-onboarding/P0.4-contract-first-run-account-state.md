Phase: 0 · Foundations and contracts

## Goal
Produce a reviewable unified diff against `docs/api-contract.md` that gives `GET /v1/me` an explicit
`onboardingState`, confines nullable identity to mid-onboarding, and removes the raw-ID fallback
from contracted behavior — without touching the contract itself.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. This is a DRAFT-ONLY ticket: contract edits are
human-only (`docs/loop-protocol.md` line 92, "Never edit `docs/api-contract.md`"; landing is the
P0.8 gate). Today the contract describes `GET /v1/me` in one line ("current user + own profile +
settings", `docs/api-contract.md` line 271) while the implementation emits raw ids:
`apps/api/src/dto/profiles.ts` line 9 passes `username` through nullable and line 10 falls back
`displayName: user.displayName ?? user.username ?? user.id`; `dto/recipes.ts` lines 36–37 and
`dto/social.ts` lines 35–36 do the same for creator/actor projections.
`apps/api/test/profiles.test.ts` lines 93–94 pin the current behavior — a fresh user gets `username:
null, displayName: 'usr_alice'` — while Swift's `UserProfile` requires non-optional `username`
(`SavoroIOS/Savoro/Core/Models/SocialModels.swift` line 14), so the first live `GET /v1/me` for a
fresh user is a decode error. The diff resolves this at the contract layer. This ticket is
deliberately scoped so another fresh agent can verify and land it independently.

## Approach
1. Write the contract changes as an exact unified diff against the current `docs/api-contract.md`,
   with `a/docs/api-contract.md` / `b/docs/api-contract.md` paths so `git apply` resolves from the
   repo root.
2. Expand the `GET /v1/me` entry (Profiles & social section) into a full response spec that adds an
   explicit `onboardingState` enum. Propose exact spelling — recommended: `accountCreated →
   usernameSet → complete` (three values; profile-basics and targets are optional steps that do not
   gate completion, per `_DESIGN.md` locked decisions 4–8). If you choose different values, justify
   each in the diff's prose.
3. Specify: identity fields (`username`, `displayName`) are nullable ONLY while `onboardingState` is
   not `complete`; `username` is required (non-null) at completion; completed profiles never carry
   null identity.
4. Remove the raw-ID fallback from described behavior: the contract must state that raw user ids
   never appear as `username` or `displayName` in any DTO (`/v1/me`, recipe `creator`, activity
   `actor`) — pre-completion public projections carry explicit nulls or are excluded, not id
   fallbacks.
5. Cover the resume semantics `_DESIGN.md` §4 requires: `onboardingState` is server-authoritative
   and drives client resume after relaunch/reinstall.
6. Validate mechanically: `git apply --check
   docs/tickets/01-onboarding/drafts/contract-first-run.diff` must pass against the current file.
