# P2.4 — Implement POST /v1/auth/login

Phase: 2 · Backend auth
Track: backend
Execution: **autonomous**
Depends on: P2.3
Supersedes: OB-14

## Goal
Land email/password login that issues the shared opaque session on success and returns byte-identical 401s for wrong-password and unknown-email.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. After P2.3, `apps/api/src/routes/auth.ts` hosts `/apple` and `/signup`, both issuing sessions through the shared helper extracted from `createSessionForAppleUser` (`src/repo/sessions.ts` — envelope `{ sessionToken, user: { id, email, displayName } }`). Verification uses `verifyPassword` from `src/lib/passwords.ts` (P2.2, constant-time). The error envelope shape is fixed: `errorResponse` (`src/errors.ts`, lines 22–24) emits `{ error: { code, message } }`, and `unauthorized` maps to 401. The security property this ticket owns: an attacker probing emails must learn nothing — unknown email and wrong password produce indistinguishable responses (same status, same body). This ticket is deliberately scoped so another fresh agent can verify and land it independently.

## Files
- `apps/api/src/routes/auth.ts`
- `apps/api/src/repo/sessions.ts` (lookup-by-normalized-email helper if P2.3 did not already add one)
- `apps/api/test/auth-login.test.ts` (new)

Login only; logout/revocation is P2.5, expiry tests are P2.6 — do not absorb them.

## Approach
1. Read the approved contract in `docs/api-contract.md` for the login request body and error taxonomy (401 bad credentials, per OB-2's drafted taxonomy — confirm the approved wording).
2. Route `auth.post('/login', …)`: parse body (malformed → 422 `validation_failed`, matching the style at `routes/auth.ts` lines 11–14); normalize the email exactly as signup does; look up the user; verify the password with `verifyPassword` against the stored P2.1 columns; on success issue a session via the shared helper and return the shared envelope.
3. Failure path — one exit: unknown email, email present but Apple-only (no password columns set), and wrong password all throw the SAME `ApiError('unauthorized', <one fixed message>)`. Structure the code so there is a single failure `throw` site; do not compose the message from which check failed.
4. Timing hygiene: on unknown email, still burn a PBKDF2 verification against a dummy stored value so response timing does not trivially distinguish the branches. Note this in a code comment; a timing test is not required.
5. Tests in `test/auth-login.test.ts`:
   - success: signup then login → 200, shared envelope, token works against `GET /v1/logs/day?date=2026-06-10` (the `test/auth.test.ts` probe);
   - wrong password → 401;
   - unknown email → 401;
   - **indistinguishability**: capture both failure responses; assert `status` strictly equal AND the full JSON bodies deeply equal (name it, e.g. `'login failures are indistinguishable'` — it is the negative-witness target);
   - case-variant email of an existing account logs in (normalization symmetry with signup);
   - each login issues a fresh token (two logins → two distinct working tokens; sessions are rows, not singletons).

### Implementation sketch
```ts
// routes/auth.ts — single failure exit, dummy-verify on unknown email
const user = await findUserByNormalizedEmail(db, email)
const stored = user?.passwordHash ? credentialOf(user) : DUMMY_CREDENTIAL // burns PBKDF2 either way
const ok = await verifyPassword(password, stored)
if (!user || !user.passwordHash || !ok) {
  throw new ApiError('unauthorized', 'Email or password is incorrect.') // the ONLY failure site
}
return c.json(await issueSession(db, user))
```

## Done when
- All test categories pass; full suite + typecheck green; no change to the Apple or signup tests.
- Success envelope is field-identical in shape to `/apple` and `/signup` (locked decision 1).
- Wrong-password and unknown-email responses are byte-identical in status and body, pinned by the named test.
- No new error code introduced; failures reuse `unauthorized` (`src/errors.ts`).
- Required negative witness: in a scratch copy, make the unknown-email branch return `ApiError('not_found', …)` (404) — `'login failures are indistinguishable'` goes red. Record the exact red assertion, restore, rerun green.

## Watch out
- The single-exit failure structure is the point: two `throw` sites with hand-matched strings will drift. If review finds two sites, that is rework.
- No lockout, rate limiting, or reset hints at MVP (locked decision 2) — the 401 message must not suggest "reset your password" (nothing to reset) and must pass the banned-copy rules (no "failed").
- Apple-only accounts (email set, password columns NULL — every pre-P2.3 user) must fall into the same 401, not a 500 from verifying against NULL; test this via a `test/seed.ts`-seeded user.
- Do not log the email or password of failed attempts.
- If the approved contract specifies a different failure code or a distinguishable taxonomy (it should not — OB-2 drafted indistinguishable 401s), the contract is the authority; if it genuinely conflicts with the locked design, mark blocked quoting both texts rather than picking one.
