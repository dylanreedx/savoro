# P7.3 — Hold Dylan's visual review of the onboarding surfaces

Phase: 7 · Journeys and gates
Track: meta
Execution: **supervised**
Depends on: P7.2

## Goal
Dylan renders a verdict — approval, redlines, or block — on every onboarding-program surface against the approved P0.7 design pack before any Checkpoint A work dispatches.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. This is human gate 3 of 5 (`_DESIGN.md` §9):
deterministic gates certify decoding, state machines, geometry, and copy — not beauty; Dylan owns
visual verdicts (locked decision 15). The evidence base is the committed snapshot references under
`SavoroIOS/SavoroTests/__Snapshots__/SnapshotTests/` (36 references existed at program authoring;
P5/P6 tickets grew the set deliberately via `SavoroIOS/Scripts/record-snapshots.sh`, which pins the
expected count) plus a live simulator walkthrough using the P7.1 journeys. The comparison target is
the P0.7 onboarding design pack as approved (or redlined) at P0.8. This ticket is deliberately
scoped so another fresh agent can verify and land it independently — its output is a recorded
verdict, not code.

## Files
- `docs/tickets/01-onboarding/_LEDGER.md` (one row updated by the orchestrator with the verdict)
- new redline packets under `docs/tickets/01-onboarding/` only if Dylan issues redlines

This fence is record-keeping only; no application code, snapshots, or scripts change in this
ticket — fixes arising from redlines get their own packets.

## Approach
1. The loop stops when this row becomes first eligible (`_RUNBOOK.md`, supervised row procedure).
   Nothing in P8 dispatches before Dylan's verdict is recorded.
2. Orchestrator assembles the review pack for Dylan:
   - all six onboarding screens (welcome/auth, email credential forms, username page, profile
     basics, intent, targets),
   - the goal-less Today,
   - the Profile account screen,
   each in the full matrix {light, dark} × {standard, XXXL} — pulled from the committed snapshot
   references, with file paths listed per screen per mode.
3. Orchestrator prepares the simulator walkthrough: boot the iPhone 17 simulator, run the P7.1
   journeys, and hand Dylan the per-step screenshots from `SavoroIOS/.ui-artifacts/onboarding/`
   plus instructions to drive the flow himself.
4. Dylan reviews against the approved P0.7 design pack and `docs/loop-protocol.md`'s visual
   quality bar (no wrapped pills/buttons, equal sibling heights, nothing clipped at XXXL, token
   spacing, ≥44pt targets, every named state evidenced).
5. Record exactly one of:
   - **approval** — ledger row `done` with the reviewed snapshot list and Dylan's words;
   - **redlines** — each redline becomes a new packet (appended, never renumbering existing rows);
     this row records the redline→packet mapping and stays gating until Dylan says the redline set
     is complete;
   - **block** — ledger row `blocked` with Dylan's reasons; the P8 chain stays closed.

## Done when
- Dylan has seen all eight surfaces in all four modes AND driven or watched the simulator flow.
- The `_LEDGER.md` row for P7.3 records the explicit verdict, timestamp, evidence paths, and — for
  redlines — the list of newly created packets.
- The loop did not dispatch any P8.x row before the verdict landed.

## Watch out
- The loop must stop and report when this row is first eligible; it never marks a supervised row
  done on Dylan's behalf (`_DESIGN.md` §9, `_RUNBOOK.md`).
- If any of the eight surfaces lacks a committed reference in any of the four modes, that is a
  gate failure of the owning P5/P6 ticket — mark this row **blocked** with the missing-file list
  as evidence; do not record snapshots here to fill the gap.
- Do not re-record references during review; re-recording belongs only to the ticket that owns
  them (never-weaken-a-gate rule).
- Agents have no eyes here either — the orchestrator presents images; it does not summarize them
  in place of Dylan looking.
- If the P0.7 design pack was redlined at P0.8, review against the redlined version, not the
  original draft; cite which version in the ledger.
