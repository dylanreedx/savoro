# P5.6 — Build the calories-first targets page

Phase: 5 · Onboarding UI
Track: frontend
Execution: **autonomous**
Depends on: P5.5
Supersedes: OB-33

## Goal
Ship the targets step: the user enters one calorie number, the app proposes an editable
protein/carb/fat split, and submits all four via the unchanged `POST /v1/goals` — with Skip as a
prominent, guilt-free first-class path.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. Locked decisions 6 and 7. The contract is
verified in `apps/api/src/routes/goals.ts`: `REQUIRED_TARGETS = ['calories', 'proteinGrams',
'carbsGrams', 'fatGrams']` (line 37); each must be a finite number > 0 or the route throws
`validation_failed` (lines 48–54); `startDate` (YYYY-MM-DD) is required (lines 67–69); the route
exposes only `GET /current` and `POST /` — no PATCH/DELETE. Skip means NO request at all: the nil
goal downstream is P6.1/P6.2's designed state. Build the calorie/split editor as a reusable
component — P6.3's Profile screen reuses it. All P5 screens build ONLY after the P0.8 design verdict
and must match the approved design pack in docs/tickets/01-onboarding/design/. This ticket is
deliberately scoped so another fresh agent can verify and land it independently.

## Approach
1. `CaloriesFirstTargetsEditor`: one calories field; on a valid entry, derive a default split of 30%
   protein / 40% carbs / 30% fat by calories, converted to grams (protein `cal × 0.30 / 4`, carbs
   `cal × 0.40 / 4`, fat `cal × 0.30 / 9`, rounded to whole grams) — confirm the default percentages
   against the approved design pack and adjust if it specifies others. All three gram fields are
   directly editable after derivation; edits stop auto-derivation for that field.
2. Client validation mirrors the server exactly: all four values finite and > 0; a zero or empty
   macro blocks submit with gentle inline guidance, matching `goals.ts:48-54` semantics.
3. Submit builds `{ dailyTargets: { calories, proteinGrams, carbsGrams, fatGrams }, startDate:
   <today, YYYY-MM-DD> }` through a P4.3-style typed request to `POST /v1/goals`; on 201 the flow
   completes toward the intent-chosen landing tab.
4. Skip is a first-class, equally-weighted action (not a small text link unless the design pack says
   so): it sends nothing, sets no local goal, and completes onboarding identically. Skip copy is
   warm ("You can add targets anytime from Profile"), never framed as giving up.
5. Named states: `empty` (Skip prominent), `derived` (calories entered, proposed split shown),
   `edited` (user-adjusted macros), `submitting`, `error`.
6. Unit tests: split math (grams for 2000 kcal pinned), edit-overrides-derivation, validation mirror
   table (0, negative, non-finite, empty), exact payload shape including `startDate`, skip performs
   no request (mock client records zero sends), banned-copy assertion.
7. Snapshot every named state across the full matrix.

## Done when
- Entering calories proposes an editable P/C/F split; all four values submit through `POST
  /v1/goals` with `startDate`; payload shape pinned by a unit test.
- Client validation rejects exactly what the server rejects (finite, > 0 on all four) — mirror table
  test green.
- Skip completes onboarding with zero goal requests sent, proven by a mock-client test.
- Snapshot matrix {light,dark} × {standard,XXXL} for every named state (empty, derived, edited,
  submitting, error); all strings banned-copy-clean.
- The editor component is consumable outside onboarding (no onboarding-flow dependencies inside
  `CaloriesFirstTargetsEditor`).
- Full iOS suite green with the grown snapshot count.

## Watch out
- Banned copy list applies (no failure/failed/guilt/etc.) — Skip and validation copy are the danger
  zones; "over limit" is banned even in helper text.
- Goals contract is UNCHANGED in this program (locked decision 6): do not add fields, do not touch
  `apps/api`; `fiberGrams`/`sodiumMilligrams` stay unsent (they are optional server-side,
  `goals.ts:38`).
- Build from L-35 design-system primitives; no raw padding/colors.
- Rounding must never produce a 0-gram macro for plausible calorie inputs (e.g. very low calories) —
  clamp derived grams to ≥ 1 or block submit with guidance, since the server rejects `n <= 0`.
- Snapshot reference counts in `Scripts/record-snapshots.sh` grow deliberately in this ticket only;
  if the design pack's split defaults conflict with this packet, the design pack wins — record which
  you used.
