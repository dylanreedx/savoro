# P2.1 — Add password-credential columns to the users schema

Phase: 2 · Backend auth
Track: backend
Execution: **autonomous**
Depends on: P0.8
Supersedes: OB-11

## Goal
Extend the `users` table with the password hash/salt/params columns the approved P0.5 contract requires, via a hand-written D1 migration with rollback notes.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. Compiled reality corrects the epic here: `users` (`apps/api/src/db/schema.ts`, lines 4–27) ALREADY has an `email` column — `text('email').unique()`, nullable, line 8 — populated by the Apple exchange (`src/repo/sessions.ts` writes `claims.email`) and by seeds. What does NOT exist is any password storage: no hash, salt, or params columns anywhere in the table (the other columns are `id`, `appleSub`, `username`, `displayName`, `bio`, `avatarUrl`, `websiteUrl`, `instagramUrl`, `tiktokUrl`, `profileVisibility`, `createdAt`, `updatedAt`). Note also: this repo does NOT use drizzle-kit — there is no drizzle config and no generate script in `apps/api/package.json`; migrations are hand-numbered SQL files in `apps/api/migrations/` (currently `0001_init.sql` … `0011_foods.sql`) applied by Wrangler and loaded into tests by `vitest.config.ts` via `readD1Migrations`. This ticket is deliberately scoped so another fresh agent can verify and land it independently.

## Files
- `apps/api/migrations/0012_password_credentials.sql` (new; verify next number)
- `apps/api/src/db/schema.ts`

Schema + migration only; no routes, no hashing module, no endpoint logic — those are P2.2/P2.3, do not absorb them.

## Approach
1. Read the approved email/password contract in `docs/api-contract.md` (landed by P0.8) for the exact credential shape. Expected columns (adjust names to the contract, not to this packet): `password_hash` TEXT NULL, `password_salt` TEXT NULL, `password_params` TEXT NULL (versioned PBKDF2 params, encoded per P2.2).
2. Author `apps/api/migrations/0012_password_credentials.sql` (next free number — verify against the directory) using `ALTER TABLE users ADD COLUMN ...` statements. All three columns nullable: every existing user is Apple-only and must remain valid.
3. Include a header comment with rollback notes: D1/SQLite supports `ALTER TABLE users DROP COLUMN <col>` for these plain columns; state the three drop statements explicitly and note that dropping destroys credentials irreversibly.
4. Mirror the columns in `apps/api/src/db/schema.ts` on the `users` table (e.g. `passwordHash: text('password_hash')`, etc.), matching existing style — nullable `text` columns, camelCase TS / snake_case SQL.
5. Email case-normalization: the contract requires unique, case-normalized email. The existing DB constraint is `unique()` on the raw column (schema.ts line 8). Per the approved contract, normalization (lowercase/trim) is enforced at write time in P2.3's signup path; add a DB-level guard here ONLY if the approved contract explicitly demands one (e.g. a unique index on `lower(email)`) — otherwise leave the constraint as-is and note the decision.
6. Run the suite: vitest applies all migrations to a fresh D1, so a malformed 0012 fails loudly.

### Implementation sketch
```sql
-- 0012_password_credentials.sql
-- Adds nullable email/password credential columns (approved P0.5 contract).
-- Existing rows are Apple-only and remain valid with all three columns NULL.
-- Rollback (destroys credentials irreversibly):
--   ALTER TABLE users DROP COLUMN password_hash;
--   ALTER TABLE users DROP COLUMN password_salt;
--   ALTER TABLE users DROP COLUMN password_params;
ALTER TABLE users ADD COLUMN password_hash TEXT;
ALTER TABLE users ADD COLUMN password_salt TEXT;
ALTER TABLE users ADD COLUMN password_params TEXT;
```

```ts
// schema.ts users table additions (after line 8's email column)

```

## Watch out
- Do not add or alter the `email` column — it already exists (schema.ts line 8); the epic's claim that it doesn't is stale. If the live column differs from what you read here, mark blocked with the observed `PRAGMA table_info(users)` output.
- Do not introduce drizzle-kit or a generated-migration workflow; hand-written SQL matching files 0001–0011 is the repo pattern.
- Columns must be nullable with no DEFAULT that implies a credential; a NOT NULL column would break every existing Apple-only row.
- Do not run any remote migration command here — preview migration application belongs to the P1 track's runbook flow.
- If P0.8's approved contract specifies different column names or an extra column (e.g. a single encoded hash string instead of three columns), the contract wins — follow it exactly and note the delta from this packet.
