# P0.6 — Draft the catalog-food logging and nutrient-map contract diff

Phase: 0 · Foundations and contracts
Track: backend
Execution: **autonomous**
Depends on: P0.1
Supersedes: OB-3 (docs/epics/onboarding.md)

## Goal
Produce a reviewable unified diff against `docs/api-contract.md` adding a catalog variant of food
logging whose frozen nutrition is an extensible keyed nutrient map, so micronutrients never force a
frozen-log migration.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. Draft-only: contract edits are human-only
(`docs/loop-protocol.md` line 92; landed at P0.8), and implementation belongs to the Checkpoint B
program, not this one (`_DESIGN.md` §2 item 10, §8) — this ticket exists so all three contract
approvals batch in one review. Today `POST /v1/logs/foods` is manual-only: the client supplies
`displayName` + macros and the server freezes them verbatim (`docs/api-contract.md` lines 176–196;
`apps/api/src/routes/logs.ts` lines 113–156). The contract's nutrition vocabulary is exactly
`calories`, `proteinGrams`, `carbsGrams`, `fatGrams` plus optional `fiberGrams`, `sodiumMilligrams`
(`MacroTotals`, `docs/api-contract.md` lines 29–42; enforced as `REQUIRED_MACROS`/`OPTIONAL_MACROS`
at `routes/logs.ts` lines 110–111). Catalog foods already have read endpoints (`GET
/v1/foods/search`, `GET /v1/foods/:id` — contract lines 262–264). This ticket is deliberately scoped
so another fresh agent can verify and land it independently.

## Approach
1. Write an exact unified diff against current `docs/api-contract.md` (`a/docs/api-contract.md`
   paths, applies from repo root), extending the `POST /v1/logs/foods` section (lines 176–196) with
   a catalog variant.
2. Catalog request: `{ "foodId", "servingId", "quantity", "date", "mealType" }`. The server resolves
   the food and serving, computes nutrition for the quantity, and freezes it server-side —
   client-supplied nutrition is ignored on this path (mirroring the recipe-log freezing rule at
   contract line 125). `servingId` must belong to `foodId` (else `validation_failed`); unknown
   `foodId` → `not_found`. Specify how the two request variants are distinguished (presence of
   `foodId` vs `displayName`+`macros`) and that mixing them is `validation_failed`.
3. Specify the frozen-nutrition evolution: the snapshot's nutrition is an extensible keyed nutrient
   map — keys are nutrient identifiers, the four macros (`calories`, `proteinGrams`, `carbsGrams`,
   `fatGrams`) are REQUIRED keys, all other keys (starting with `fiberGrams`, `sodiumMilligrams`)
   are optional and open-ended. New nutrients are additive: readers ignore unknown keys, and
   existing frozen logs never migrate.
4. State compatibility explicitly: the map's required keys make it a superset of today's
   `MacroTotals`, so existing manual logging and day-total semantics are unchanged.
5. Mark the section as approved-but-deferred: implementation is the Checkpoint B program; nothing in
   this program builds it.
6. Validate with `git apply --check`.

## Watch out
- Do NOT edit `docs/api-contract.md` or implement anything in `apps/api/` — a route handler, schema
  change, or test here is an out-of-fence edit.
- Do not redesign the existing manual variant or `MacroTotals` shape; the map extends the vocabulary
  without breaking current readers (frozen snapshots are an ADR invariant).
- Do not spec micronutrient display, targets, or USDA import — explicit non-goals (`_DESIGN.md` §8);
  the draft only makes them cheap later.
- Each draft in `drafts/` must apply against the CURRENT contract independently; ordering conflicts
  among the three diffs are resolved by Dylan at P0.8, not by chaining diffs.
- If the packet conflicts with compiled reality (e.g. the logs route or contract section has changed
  since authoring), rebuild the diff on what the repo actually shows, or mark blocked with evidence
  if a locked decision is contradicted.
