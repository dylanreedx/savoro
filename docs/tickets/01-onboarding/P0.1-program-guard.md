# P0.1 — Build the program integrity guard

Phase: 0 · Foundations and contracts
Track: meta
Execution: **autonomous**
Depends on: —
Supersedes: —

## Goal
A `scripts/check-onboarding-program.sh` that mechanically validates the 01-onboarding program's own
bookkeeping — queue, ledger, and packet headers — before any feature ticket runs on top of it.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. The loop selects work by parsing `_QUEUE.md` and
`_LEDGER.md` (`_RUNBOOK.md`, "Ticket selection"); if those files drift — a deleted row, a forged
execution mode, a dependency naming a ticket that does not exist — the loop dispatches wrong work
silently. `_QUEUE.md` declares exactly 50 rows (lines 13–62), `_LEDGER.md` mirrors the same 50
tickets with states `pending | in-progress | done | blocked` (its "## states" section), and exactly
5 rows are supervised: P0.8 (queue line 20), P1.2 (line 22), P7.3 (line 56), P8.4 (line 60), P8.5
(line 61). The `scripts/` directory does not exist yet; this ticket creates it. This ticket is
deliberately scoped so another fresh agent can verify and land it independently.

## Files
- `scripts/check-onboarding-program.sh` (new; create `scripts/` as needed)

This fence is a single new script; the guard must never "fix" the program it checks, so `_QUEUE.md`,
`_LEDGER.md`, and packet files stay untouched. Do not absorb adjacent work (P0.2's STATUS.md fixes,
P0.3's preland script).

## Approach
1. Write a bash script (`set -euo pipefail`) that takes an optional program-directory argument,
   defaulting to `docs/tickets/01-onboarding` relative to the repo root (resolve the root from the
   script's own location, not `$PWD`). The argument exists so negative-witness runs can point at a
   mutated copy while the live program stays untouched.
2. Parse the `_QUEUE.md` table and assert: exactly 50 data rows; ticket filenames unique; every
   named packet file exists in the program directory.
3. Assert every entry in each row's "Depends on" cell is either `—` or a `P<phase>.<n>` id that maps
   to another row's ticket filename (`P0.1` ↔ `P0.1-program-guard.md`).
4. Parse the `_LEDGER.md` table and assert: exactly the same 50 ticket filenames, no extras or
   omissions; every state is one of `pending|in-progress|done|blocked`.
5. For each packet file, assert the header carries all four required fields — `Phase:`, `Track:`,
   `Execution:`, `Depends on:` — and that Execution and Depends on match the queue row exactly.
   Track words map to queue letters: backend=B, frontend=F, integration=I, meta=M.
6. Assert exactly 5 queue rows are `supervised` and that they are exactly P0.8, P1.2, P7.3, P8.4,
   P8.5 — no more, no fewer, no substitutions.
7. On success print a one-line summary (rows checked, packets checked) and exit 0; on any violation
   print every violation with file and row context and exit non-zero.

## Done when
- `bash scripts/check-onboarding-program.sh` exits 0 against the live, fully authored program.
- Failures are reported with enough context (file, ticket, expected vs found) to fix by hand.
- Required negative witness: at least 5 isolated mutations, each applied to a scratch copy of the
  program directory, each observed red at the specific assertion it targets, with the live program
  untouched throughout:
  1. a deleted queue row → red at the 50-row count;
  2. a duplicated ticket filename row → red at the uniqueness check;
  3. an invalid ledger state (e.g. `paused`) → red at the state whitelist;
  4. a queue row pointing at a missing packet file → red at the existence check;
  5. a supervised row forged to autonomous (P0.8 in the copy) → red at the supervised-set check.
  Each mutation is applied alone, observed red, and the copy discarded or restored before the next.

## Verify
```bash
bash scripts/check-onboarding-program.sh
```
Record in `_LEDGER.md`: the green exit 0 run, and for each of the 5 witness mutations the exact
failing assertion message. Confirm `git status` shows only the new script.

## Watch out
- The guard checks; it never mutates. Any "auto-repair" behavior is out of scope and a rework
  trigger.
- Do not hardcode the count 50 into a comparison against the ledger separately from the queue — the
  two files must be cross-checked against each other, not each against a constant only.
- Markdown table parsing is brittle: anchor on the `| n | \`P...\` |` row shape, not on line
  numbers, so future prose edits above the table don't break the guard.
- Run witness mutations only against a copy in the scratch directory; touching the live
  `_QUEUE.md`/`_LEDGER.md` is an out-of-fence edit and stops the loop.
- If, at execution time, the live program genuinely fails a check (e.g. a packet file is actually
  missing), that is a real program defect: mark this ticket blocked with the guard's output as
  evidence rather than weakening the check to pass.
