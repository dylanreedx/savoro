# P5.3 — Build the username page

Phase: 5 · Onboarding UI
Track: frontend
Execution: **autonomous**
Depends on: P5.2, P3.2
Supersedes: OB-30

## Goal
Ship the dedicated username page shown immediately after account creation for BOTH auth methods,
with debounced live availability, suggestions when taken, and rules copy matching the backend regex.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. Locked decision 4: every completed onboarding
has a public-capable identity; Apple provides no username either, so this page is unconditional. The
backend rule is verified at `apps/api/src/routes/profiles.ts:72`:
`/^[a-z0-9](?:[a-z0-9_-]{1,28}[a-z0-9])$/` — 3–30 characters, lowercase letters and digits, hyphens
or underscores allowed only in the middle, must start and end alphanumeric (server error copy at
line 75: "username must be a 3-30 character lowercase URL slug."). Availability checks go through
P3.2's endpoint. All P5 screens build ONLY after the P0.8 design verdict and must match the approved
design pack in docs/tickets/01-onboarding/design/. This ticket is deliberately scoped so another
fresh agent can verify and land it independently.

## Files
- `SavoroIOS/Savoro/Features/Onboarding/UsernameView.swift` (new — view + view model with debounce)
- `SavoroIOS/SavoroTests/OnboardingTests.swift` (extend — rules mirror, debounce, suggestions, copy)

## Approach
1. Build `UsernameView` from L-35 primitives: one text field (lowercased, autocorrect off), a live
   status line, rules copy, and a continue button enabled only on `available`.
2. Mirror the exact backend regex client-side for instant local feedback; keep it in one constant
   the tests assert against, so a drift from `profiles.ts:72` is caught deliberately, not silently.
3. Debounce availability calls (≈300 ms after typing pauses, only for locally-valid candidates)
   through the P3.2 typed request; named field states: `empty`, `checkingAvailability`, `available`,
   `taken` (with 2–3 suggestions, e.g. suffixed variants that themselves pass the regex), `invalid`
   (rules copy highlighted).
4. Rules copy in plain words: "3–30 characters. Lowercase letters, numbers, hyphens, or underscores
   — starting and ending with a letter or number." No regex or backend jargon on screen.
5. Submit via `PATCH /v1/me/profile` (P4.3 typed request); on success the P4.5 state machine
   advances per the server's `onboardingState`.
6. Unit tests: regex-mirror acceptance/rejection table (include edge cases `ab`, `-abc`, `abc-`, 31
   chars, uppercase); debounce fires once for a burst of keystrokes; suggestions are regex-valid;
   banned-copy assertion over all visible strings.
7. Snapshot every named state across the full matrix.

## Done when
- The page renders after account creation for both the Apple and email paths (state-machine unit
  test proves both routes land here).
- Availability is live and debounced; a taken name shows calm copy plus valid suggestions; `invalid`
  shows the rules without shaming.
- Client rule matches `profiles.ts:72` exactly, proven by a shared-constant test table.
- Snapshot matrix {light,dark} × {standard,XXXL} for every named state (empty, checkingAvailability,
  available, taken, invalid); all strings banned-copy-clean.
- Full iOS suite green with the grown snapshot count.

## Watch out
- Banned copy list applies (no failure/failed/guilt/etc.) — "taken" copy should read as "that one's
  in use — here are some close ones", not rejection.
- Build from L-35 design-system primitives; no raw padding/colors.
- Verify P3.2's actual availability surface (dedicated endpoint vs documented 422-probe) as landed
  before writing the request call; follow compiled reality and note any delta.
- Never display a raw user id as a fallback identity anywhere on this screen (locked decision 5).
- Snapshot reference counts in `Scripts/record-snapshots.sh` grow deliberately in this ticket only;
  if the approved design pack conflicts with the backend regex, the backend wins — mark blocked with
  evidence if they cannot be reconciled.
