# P5.7 — Make interrupted onboarding resume at the correct step

Phase: 5 · Onboarding UI
Track: integration
Execution: **autonomous**
Depends on: P5.6, P3.3
Supersedes: OB-34

## Goal
Interrupted onboarding resumes at the correct step after relaunch AND reinstall, driven by the
server's `onboardingState` via `GET /v1/me`, and completed onboarding never reappears.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. The server is the authority for resume routing
(locked decision 5 / P3.3): `GET /v1/me` carries an explicit `onboardingState`, and the P4.5 root
state machine must map every server state to a step — account created → username page; username set
→ profile basics; profile done → intent/targets (client-side steps, not server-encoded, per locked
decision 8); completed → authenticated tabs, never onboarding again. Reinstall is the hard case: the
Keychain session may survive app deletion, so a fresh install with a live session must still ask the
server where the user is. P3.4's minted accounts exist so tests never hand-roll SQL. This ticket is
deliberately scoped so another fresh agent can verify and land it independently.

## Files
- `SavoroIOS/Savoro/App/` root state machine file(s) as landed by P4.5 (resume mapping only)
- `SavoroIOS/SavoroTests/OnboardingTests.swift` (extend — resume mapping unit tests)
- `SavoroIOS/SavoroUITests/SavoroSmokeJourneyTests.swift` (add a relaunch resume journey; or a

This fence is resume behavior plus its proof; do not absorb adjacent work (no new screens, no server
changes, no expired-session UX — that is P5.8).

## Approach
1. Read the P4.5 state machine and P3.3's landed `onboardingState` values first; enumerate the real
   states from code, not from this packet.
2. Implement (or verify, if P4.5 already did) `step(for onboardingState:)` as a pure function; on
   every cold launch with a stored session, call `GET /v1/me` and route from the response — never
   from cached local step state alone.
3. Cover the intent/targets client-side tail: a user who completed the server-visible steps but quit
   before intent/targets resumes at intent (server says profile complete but onboarding not marked
   complete — align with P3.3's completion semantics; if the server has no such distinction, resume
   at the first client-side step and record that decision).
4. Unit tests: one case per `onboardingState` value → expected step; completed → authenticated with
   no onboarding UI; unknown/future state → safe default (earliest incomplete step), not a crash.
5. XCUITest relaunch case against the local Worker: mint a mid-onboarding account via P3.4 tooling,
   launch, land on the expected step, terminate via `XCUIApplication.terminate()`, relaunch, assert
   the same step reappears; then complete onboarding, relaunch, assert tabs and no onboarding UI.
   Capture per-step screenshots.
6. Simulate reinstall in-unit-test by clearing all state except the Keychain-backed session (fake
   Keychain from P4.1 tests) and asserting the server-driven route still resolves.

## Done when
- A pure resume-mapping function has a unit test per real `onboardingState` value, plus
  completed-never-reappears and unknown-state-safe cases.
- The reinstall shape (session present, local state absent) resolves the correct step from `GET
  /v1/me` in a unit test.
- The XCUITest relaunch journey passes against the local Worker with a P3.4-minted mid-onboarding
  account, with screenshots recorded per step.
- Required negative witness: hard-code the resume path to always return the first step (ignoring
  `onboardingState`) → the mapping unit tests AND the relaunch journey go red; restore and rerun
  green. Record the exact red assertion.
