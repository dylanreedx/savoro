# P3.1 — Implement onboardingState and remove the raw-ID fallback

Phase: 3 · Backend first-run profile
Track: backend
Execution: **autonomous**
Depends on: P0.8
Supersedes: OB-18

## Goal
`GET /v1/me` carries an explicit `onboardingState` per the P0.8-approved contract, and no DTO mapper
ever emits a raw user id as a user-visible string.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. Verified today:
`apps/api/src/dto/profiles.ts:10` is `displayName: user.displayName ?? user.username ?? user.id`
(line 9 leaves `username` raw and nullable — that stays nullable mid-onboarding);
`apps/api/src/dto/recipes.ts:36-37` has `username: owner.username ?? owner.id` and `displayName:
owner.displayName ?? owner.username ?? owner.id`, with a comment at lines 33-35 documenting the
fallback as intentional; `apps/api/src/dto/social.ts:35-36` repeats both in `mapActivityItem`.
Existing tests assert the OLD behavior: `apps/api/test/profiles.test.ts:94` and `:158` expect
`displayName: 'usr_alice'`, and `:318-324` (comment plus assertion) expects `creator.username` to be
`'usr_bob'` after nulling the username. Updating those assertions is the intentional behavior change
this ticket delivers, not a regression. This ticket is deliberately scoped so another fresh agent
can verify and land it independently.

This fence covers the three mappers, the `/v1/me` surface, and the tests that pin them; do not
absorb adjacent work (no username-availability endpoint — that is P3.2).

## Approach
1. Read the approved `docs/api-contract.md` section from the P0.8 commit for the exact
`onboardingState` enum values and where they sit in the `GET /v1/me` envelope. Implement exactly
that shape in `mapMe` (`dto/profiles.ts:25-37`). Derivation is server-side from the user row (e.g.
username set, profile completed), per the contract.
2. Delete every `?? user.id` / `?? owner.id` / `?? rows.actor.id` fallback in the three mappers. Per
the locked decision, identity is nullable ONLY mid-onboarding: emit `null` (or whatever the approved
contract specifies) instead of the raw id. Remove the now-false comments at `dto/recipes.ts:33-35`
and `dto/profiles.ts` where they document the fallback.
3. Update `profiles.test.ts:86-100` (fresh user `displayName`), `:158`, and `:318-324` to assert the
new contract, including `onboardingState` for a fresh seeded user versus a completed one.
4. Add a raw-id regression test: seed users/recipes/activity, fetch `/v1/me`, a recipe detail, and a
public profile, then walk every string field of each JSON body and assert none equals a seeded user
id (`usr_alice`, `usr_bob`). The `collectKeys`-style recursive walk in `profiles.test.ts:56-66` is a
good model.
5. Run the negative witness, record it, restore.

### Implementation sketch
```ts
// dto/recipes.ts creator projection after the change
creator: {
  userId: owner.id,
  username: owner.username,            // null mid-onboarding only
  displayName: owner.displayName ?? owner.username,  // per approved contract
  avatarUrl: owner.avatarUrl,
},
```
(Exact nullability of `displayName` comes from the approved contract; do not invent a placeholder string.)

## Done when
- `GET /v1/me` returns `onboardingState` matching the approved contract for at least: fresh account,
  username set, completed.
- No `?? user.id`-style fallback remains in `dto/profiles.ts`, `dto/recipes.ts`, or `dto/social.ts`
  (grep is clean).
- Updated tests assert the new contract; the raw-id regression test walks recursive JSON and rejects
  any string field equal to a seeded user id.
- `bun run test && bun run typecheck` green.
- Required negative witness: reintroduce `?? user.id` in exactly one mapper against the final code →
  the raw-id regression test goes red with a named assertion; restore; rerun green.

  `creator.username` as non-null; fix only the assertions your change actually breaks, and list them
