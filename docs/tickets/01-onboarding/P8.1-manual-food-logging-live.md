# P8.1 — Build the real manual food-logging form against the live logs API

Phase: 8 · Checkpoint A
Track: integration
Execution: **autonomous**
Depends on: P7.3
Supersedes: OB-46

## Goal
A real manual-food form (name, calories/P/C/F, meal and date) submits to the live logs API, with edit and delete of entries, full state coverage, and live-journey proof.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. The server contract is verified in
`apps/api/src/routes/logs.ts`: `POST /v1/logs/foods` (lines 113–156) takes `displayName`, `macros`
(`calories`, `proteinGrams`, `carbsGrams`, `fatGrams` required non-negative; `fiberGrams`,
`sodiumMilligrams` optional), `date` (YYYY-MM-DD), `mealType`, `quantity`, `quantityUnit`, and
returns 201 `{ entry, dayLog }`. `PATCH /v1/logs/:entryId` (lines 158–165, parser 172–204) allows
ONLY `date`, `mealType`, `quantity`; `DELETE /v1/logs/:entryId` (167–170) returns 204. The iOS
side already has `LogFoodRequest`/`LogFoodRequestPayload` matching the POST shape
(`SavoroIOS/Savoro/Core/API/LoggingRequests.swift` lines 93–116); no PATCH/DELETE typed requests
exist yet. Frozen snapshots mean name/macros are immutable after logging — "edit" is
move/requantify, not rewrite. This ticket is deliberately scoped so another fresh agent can verify
and land it independently.

## Files

degraded states (P8.3) are adjacent tickets — do not absorb them.

## Approach
1. Build the form from L-35 design-system primitives per the approved design pack: name, calories,
   protein, carbs, fat, meal picker, date picker; inline validation mirroring the server taxonomy
   (non-empty name, non-negative finite macros, positive quantity).
2. Submit through the existing authenticated environment via `LogFoodRequest` (target `.live` →
   `/v1/logs/foods`); apply the returned `dayLog` to Today exactly as `applyLogResponse` does.
3. Add typed `PATCH /v1/logs/:entryId` (fields: `date`, `mealType`, `quantity` only) and
   `DELETE /v1/logs/:entryId` requests with contract-exact request tests; wire entry actions
   (edit sheet limited to those three fields; calm delete confirmation).
4. Cover named states — normal, loading, error, validation-error — in unit tests and the snapshot
   matrix {light,dark} × {standard,XXXL}; grow the pinned count in
   `SavoroIOS/Scripts/record-snapshots.sh` deliberately.
5. Extend the P7.2 live journey: after onboarding, create a manual food entry, see totals change,
   edit its meal/date, delete it, see totals restore — all against the local Worker.
6. Run the banned-copy grep over every new string.

## Done when
- Manual entry created from the form appears in the live Today with server-computed totals.
- Edit is limited to date/meal/quantity (matching lines 178–182 of `logs.ts`); name/macros are
  presented as fixed once logged — no UI promises the server refuses.
- Delete removes the entry (204) and Today reflects it.
- Every named state has all four snapshot modes; pinned snapshot count grown in this ticket only.
- Live journey covers create→edit→delete green against the local Worker.

## Watch out
- Spec drift alert: the epic's "edit via logs-management endpoints" does NOT mean editing macros —
  the server's PATCH allowlist is `date`, `mealType`, `quantity` (verified). If the approved
  design pack promises macro editing, mark **blocked** with the routes evidence for Dylan.
- No banned copy: deletion/validation states must stay calm — no "failed", no guilt.
- Do not route through `/mock/…` in the shipped path; `MockAPIClient.localMockSuccessRoutes()`
  mirrors exist for previews/tests only (locked decision 12).
- `mealType` values are `breakfast|lunch|dinner|snack` (logs.ts line 22); don't invent others.
- Keep P7.1's deterministic journeys green; if identifiers move, update assertions in the same
  commit, never by weakening them.
