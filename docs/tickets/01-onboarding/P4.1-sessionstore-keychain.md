# P4.1 — Build SessionStore over a Keychain token store

Phase: 4 · iOS auth core
Track: frontend
Execution: **autonomous**
Depends on: P0.8
Supersedes: OB-22 (SessionStore/Keychain half)

## Goal
A tested `SessionStore` stores, restores, and clears the opaque session token through a
protocol-backed Keychain store, with an in-memory fake for unit tests.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. Verified today: `SavoroIOS/Savoro/Core/`
contains only `API/`, `Fixtures/`, and `Models/` — **no `Core/Auth/` exists**, and no Keychain or
session code exists anywhere in the app. The only token plumbing is
`URLSessionAPIClient.authTokenProvider` (`Core/API/APIClient.swift:55-72`), an async closure
returning `String?` — SessionStore becomes the thing that closure reads from (wired in P4.3/P4.5,
not here). Locked decision 1: both auth methods converge on ONE opaque bearer session, so this store
is method-agnostic — it holds a token string, never an Apple credential. This ticket is deliberately
scoped so another fresh agent can verify and land it independently.

## Approach
1. Create `SavoroIOS/Savoro/Core/Auth/` with:
   - `TokenStoring` protocol: `func save(_ token: String) throws`, `func load() throws -> String?`,
     `func clear() throws` (sync is fine; Keychain calls are fast and the API client's provider closure
     can wrap them).
   - `KeychainTokenStore: TokenStoring` — `kSecClassGenericPassword`, a fixed service/account pair,
     `kSecAttrAccessibleAfterFirstUnlock` so a background relaunch can restore; save is upsert
     (delete-then-add or `SecItemUpdate` fallback); `load` returns nil on `errSecItemNotFound`, throws
     on other statuses.
   - `InMemoryTokenStore: TokenStoring` — a fake for tests (and later DEBUG previews).
   - `SessionStore` — owns a `TokenStoring`, exposes `storeSession(token:)`, `restoreSession() ->
     String?`, `clearSession()`, and a current-token accessor the API client's `authTokenProvider` can
     call. Keep it `final class` + `Sendable`-safe (lock or actor) since `authTokenProvider` is
     `@Sendable`.
2. Add the new files to the Savoro target the same way existing `Core/API` files are registered
(check whether the project uses file-system-synchronized groups in `Savoro.xcodeproj` before
hand-editing the pbxproj).
3. Unit tests (new `SavoroTests/SessionStoreTests.swift`, using `InMemoryTokenStore`):
   - store → restore round-trip returns the same token;
   - `clearSession()` then restore returns nil (clear-on-signout);
   - fresh-launch path: a NEW `SessionStore` over a store that already holds a token restores it
     (simulates relaunch — persistence lives in the store, not the SessionStore instance);
   - fresh install: empty store restores nil;
   - overwrite: storing token B after token A restores B.
4. Do NOT add a Keychain-hitting test to the unit suite by default; unit tests use the fake (the
packet's own requirement). The real `KeychainTokenStore` stays thin enough that its correctness is
covered by the P8 device checks.

## Files
- `SavoroIOS/Savoro/Core/Auth/TokenStoring.swift` (new)
- `SavoroIOS/Savoro/Core/Auth/KeychainTokenStore.swift` (new)
- `SavoroIOS/Savoro/Core/Auth/SessionStore.swift` (new)
- `SavoroIOS/SavoroTests/SessionStoreTests.swift` (new)
- `SavoroIOS/Savoro.xcodeproj/project.pbxproj` (only if file registration requires it)

This fence is the new Auth module plus its tests; do not absorb API-client wiring (P4.3), root-state
work (P4.5), or any UI.

## Done when
- `Core/Auth/` exists with protocol, Keychain store, in-memory fake, and SessionStore.
- All four named test behaviors pass using the fake; no unit test touches the real Keychain.
- No file outside `Core/Auth/` + tests changed (except project registration).
- No token is ever written to UserDefaults, a file, or a log statement (grep the diff).
- Full iOS suite green with the pre-existing count plus the new tests.

```bash
cd SavoroIOS && xcodebuild test -scheme Savoro -destination 'platform=iOS Simulator,name=iPhone 17'
```
Record in `_LEDGER.md`: derived unit-test count before/after, the list of new test names, and
confirmation the diff contains no UserDefaults/print of tokens.

## Watch out
- If the Xcode project rejects the new directory (target membership/pbxproj conflicts you cannot
  resolve mechanically), mark blocked with the xcodebuild error — do not scatter the files into
  `Core/API/` to dodge it.
- Keychain APIs behave differently on simulator vs device; that is exactly why the protocol + fake
  exist. Do not weaken tests to "pass on CI" by stubbing `SecItem*` globally.
- No session shape beyond an opaque `String` token — no expiry parsing, no user id caching; the
  server owns session validity (locked decision 1; expiry enforcement is P2.6 server-side).
- Match existing code style (`Sendable` annotations, no force-unwraps — see `Core/API/APIClient.swift`).
- Do not pre-build P4.2/P4.3 seams "while you're here"; SessionStore's only consumer contract is the
  accessor named above.
