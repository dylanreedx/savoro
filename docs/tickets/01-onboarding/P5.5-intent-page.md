# P5.5 — Build the intent page

Phase: 5 · Onboarding UI
Track: frontend
Execution: **autonomous**
Depends on: P5.4
Supersedes: OB-32

## Goal
Ship the one-screen intent question — three options that choose the landing tab and whether the
targets step appears — stored client-side only, with nothing persisted server-side.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. Locked decision 8: intent is a routing hint, not
identity. Exactly three options: "Track what I eat" / "Build my recipe collection" / "Both". The
selection decides (a) which tab the user lands on after onboarding and (b) whether the P5.6 targets
step is offered next. It lives in `UserDefaults` or transient app state — NO new endpoint, no `PATCH
/v1/me/profile` field, no contract surface. The server's `onboardingState` therefore cannot encode
this step; the P4.5 state machine must treat intent as a client-side interstitial, not a
server-resumable state. All P5 screens build ONLY after the P0.8 design verdict and must match the
approved design pack in docs/tickets/01-onboarding/design/. This ticket is deliberately scoped so
another fresh agent can verify and land it independently.

## Files
- `SavoroIOS/Savoro/Features/Onboarding/IntentView.swift` (new — view, view model, intent enum +
  storage)
- `SavoroIOS/SavoroTests/OnboardingTests.swift` (extend — routing table, persistence locality, copy)
- `SavoroIOS/SavoroTests/SnapshotTests.swift` (add intent-page snapshot cases)
- `SavoroIOS/Scripts/record-snapshots.sh` (bump `expected_snapshot_count`)

This fence is one client-only screen plus its evidence; do not absorb adjacent work (no targets UI —
P5.6; no networking code at all in this ticket).

## Approach
1. Define an `OnboardingIntent` enum with three cases and their exact display strings: "Track what I
   eat", "Build my recipe collection", "Both".
2. Encode the routing consequences as pure, testable functions: `landingTab(for:)` (tracking →
   Today; recipe collection → Cookbook; both → Today) and `offersTargetsStep(for:)` (true for "Track
   what I eat" and "Both"; false for "Build my recipe collection"). Confirm both mappings against
   the approved design pack before pinning tests.
3. Build `IntentView` from L-35 primitives: three selectable option cards, continue enabled after a
   selection.
4. Persist the choice in `UserDefaults` (or transient app state if the design pack prefers); it must
   never appear in any request body — assert no typed request type carries it.
5. Feed the routing result to the P4.5 state machine: continue → targets step when offered,
   otherwise complete onboarding toward the chosen landing tab.
6. Unit tests: full routing table (3 intents × landing tab × targets-offered), storage stays local,
   all three option strings pinned verbatim, banned-copy assertion.
7. Snapshot named states: `unselected`, one `selected` variant per option (or one representative if
   the design pack says the three are visually uniform — record which).

## Done when
- Exactly three options with the exact locked strings; selection drives landing tab and targets-step
  offering per a pinned unit-test routing table.
- Nothing about intent leaves the device: no endpoint call, no request payload field — proven by a
  test over the P4.3 request types this flow uses.
- Snapshot matrix {light,dark} × {standard,XXXL} for every named state; all strings
  banned-copy-clean.
- Full iOS suite green with the grown snapshot count.

## Verify

```bash
cd SavoroIOS && xcodebuild test -scheme Savoro -destination 'platform=iOS Simulator,name=iPhone 17'
```
Record references with `./Scripts/record-snapshots.sh` after bumping the pinned count. Report for

## Watch out
- Banned copy list applies (no failure/failed/guilt/etc.); intent options must not moralize ("get
  healthy", "fix my diet" are out — the three locked strings are the copy).
- Build from L-35 design-system primitives; no raw padding/colors.
- Do NOT add intent to `PATCH /v1/me/profile`, `onboardingState`, or any new endpoint — that would
  be a contract change, which is human-only (locked decision 9). If the design pack implies server
  persistence, mark blocked with evidence.
- Resume behavior after relaunch mid-intent is P5.7's problem; here just make the client state
  machine's intent step re-enterable without crashing.
- Snapshot reference counts in `Scripts/record-snapshots.sh` grow deliberately in this ticket only.
