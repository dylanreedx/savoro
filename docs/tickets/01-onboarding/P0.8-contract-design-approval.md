# P0.8 — Hold the contract and design approval gate

Phase: 0 · Foundations and contracts
Track: meta
Execution: **supervised**
Depends on: P0.4, P0.5, P0.6, P0.7
Supersedes: —

## Goal
Dylan reviews the three contract draft diffs and the onboarding design pack; approved diffs land as
dedicated `[Contract]` commits, and the design verdict is recorded before any dependent phase
dispatches.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. This is the first of the program's five
supervised rows (`_QUEUE.md` line 20) and the hard gate `_DESIGN.md` §7 step 2 names: nothing
downstream builds against an unapproved contract, and onboarding UI (P5.x) builds only after the
design verdict. `docs/api-contract.md` changes only on `main`, in a dedicated `[Contract]` commit,
with human approval (`docs/agent-workflow.md` "Source of truth"; `docs/loop-protocol.md` line 92).
The deliverables under review: `drafts/contract-first-run.diff` (P0.4),
`drafts/contract-email-password.diff` (P0.5), `drafts/contract-catalog-food.diff` (P0.6), and
`design/onboarding-design-spec.md` plus wireframes (P0.7). Per `_RUNBOOK.md` "Supervised row
procedure", the loop stops here, presents, and waits. This ticket is deliberately scoped so another
fresh agent can verify and land it independently.

## Files
- `docs/api-contract.md` (Dylan-authorized `[Contract]` commits only)
- `docs/tickets/01-onboarding/_LEDGER.md` (this row's verdict note — orchestrator-edited)
- `docs/tickets/01-onboarding/drafts/` (only if Dylan's redlines amend a diff before landing)

This fence exists because the contract is human-only territory and the ledger records the human
verdict; no other file may change, and no worker is dispatched for this row.

## Approach
1. The loop stops when this row becomes first eligible and reports to Dylan (`_RUNBOOK.md` stop
   conditions). No autonomous work proceeds past this point.
2. Present the four deliverables: the three diffs (each pre-checked with `git apply --check`) and
   the design pack, with a one-paragraph summary of what each decides.
3. Dylan reviews each diff and issues, per diff: approve, redline, or reject.
4. For each APPROVED diff, Dylan authorizes landing it as its own dedicated commit on `main`,
   message prefixed `[Contract]` — one commit per diff, three commits if all approve. Apply the diff
   verbatim (`git apply`), commit, push, per the landing protocol.
5. Dylan reviews the design pack and issues: approval, or redlines. Redlines are recorded verbatim
   and converted into new tickets (appended to the program by the orchestrator with Dylan's
   sign-off) BEFORE any dependent phase (P2/P3/P4/P5/P6) dispatches.
6. Record the full verdict in this row's `_LEDGER.md` note: per-diff decision, the three (or fewer)
   contract commit hashes, the design verdict, and any redline→ticket mappings. A rejection is
   recorded explicitly with Dylan's stated reason.
7. Only after the ledger note is complete does the loop restart.

## Done when
- Three `[Contract]` commits exist on `main` (one per approved diff), OR an explicit rejection for
  the missing one(s) is recorded in the ledger with Dylan's reasoning.
- The design verdict (approval or redlines) is in the ledger, and every redline has a corresponding
  new ticket before dependent phases dispatch.
- Dylan explicitly stated each decision in this conversation or a recorded channel — none is
  inferred.
- `docs/api-contract.md` matches exactly the approved diffs and nothing else.

## Verify
```bash
git log --oneline -5 -- docs/api-contract.md
git diff HEAD~3 --stat -- docs/api-contract.md   # adjust count to commits landed
```
Record in `_LEDGER.md`: commit hashes, per-deliverable verdicts, redline→ticket list, and the UTC
timestamp of Dylan's approval.

## Watch out
- The loop stops here and NEVER marks this row done on Dylan's behalf — approval must come from
  Dylan, explicitly, per deliverable (`_RUNBOOK.md` supervised procedure; `_DESIGN.md` §9).
- No worker edits `docs/api-contract.md`, ever. If a diff no longer applies because the contract
  moved, the fix is a re-draft ticket, not a hand-merge at the gate.
- Do not batch the three diffs into one commit; one `[Contract]` commit per diff is the
  reviewability contract.
- Do not dispatch P2.1, P2.7, P3.1, P4.1, P5.1, P6.1, or P6.2 while any of their governing approvals
  is pending or redlined-unresolved.
- Partial approval is legitimate: land what is approved, record what is not, and let the queue's
  dependency edges (all of P2–P6 depend on P0.8) hold until the ledger note says which downstream
  work is actually unblocked — if partial approval leaves that ambiguous, keep the loop stopped and
  ask Dylan rather than guessing.
