# P3.4 — Mint dev accounts in any onboarding state

Phase: 3 · Backend first-run profile
Track: backend
Execution: **autonomous**
Depends on: P3.3, P2.4
Supersedes: OB-21

## Goal
One script mints a local or preview account frozen at any onboarding state (fresh, username-set,
complete, with or without a goal) so iOS work and UI tests never hand-roll SQL.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. Verified today: the only account seeding is
`apps/api/seed/local-dev.sql` — it upserts `usr_dev_alice` (line 5), a session whose bearer token is
`dev-alice-token` (comment line 3, hash rows lines 12-26), a current goal starting at line 28 (2200
kcal / 150P / 240C / 70F), and one published recipe; it runs via `bun run db:seed:local`
(`apps/api/package.json`). It always produces one shape: complete-ish account WITH a goal — useless
for testing fresh/partial states. Locked decision 16: `seed/local-dev.sql` never runs remotely. By
queue order, P1.4's safe remote seed tooling and P2.4's `POST /v1/auth/login` are on `main`; ground
preview minting in P1.4's mechanism (read its ledger row and landed script first). This ticket is
deliberately scoped so another fresh agent can verify and land it independently.

## Approach
1. Read P1.4's landed tooling (check `_LEDGER.md` for its commit and file paths) and reuse its
credential-generation and remote-execution pattern rather than inventing a second one.
2. Add a script (e.g. `apps/api/scripts/mint-account.ts`, run via a new `package.json` script) with flags:
   - `--state fresh|username-set|complete` — writes exactly the rows that put `GET /v1/me` in that
     `onboardingState` per P3.3's landed semantics;
   - `--with-goal` / default no goal — nil-goal is the designed first-run state (locked decision 7), so
     goal-less must be the default, not an afterthought;
   - `--target local|preview` — local uses `wrangler d1 execute DB --local`; preview goes ONLY through
     P1.4's safe path.
3. Credentials: generate a random email/password (P2.4's login must accept them) and/or a session
token per P1.4's pattern; print once to stdout; never write them to a file, never commit them, never
reuse a fixed token for preview.
4. Make the state claims honest: after minting, the script calls `GET /v1/me` with the minted
credentials against the target and asserts the reported `onboardingState` matches the requested
flag, failing loudly otherwise.
5. Document usage in the script header comment (not a new markdown file). Add a vitest that
exercises the row-writing logic's state derivation if it is factored as importable functions; the
live self-check in step 4 covers the wiring.

## Files
- `apps/api/scripts/mint-account.ts` (new; name may follow P1.4's convention)
- `apps/api/package.json` (script entries only)
- `apps/api/seed/local-dev.sql` (only if P3.3's semantics require the seed to declare its own state
  explicitly)
- `apps/api/test/` (one focused test file if logic is importable)

This fence is tooling plus its registration; do not absorb endpoint changes, migrations, or iOS
launch-argument plumbing.

## Done when
- Each of `fresh`, `username-set`, `complete` (each × with/without goal) mints locally, and the
  script's own `GET /v1/me` self-check confirms the requested `onboardingState`.
- Preview minting uses only P1.4's safe path; the script physically cannot apply
  `seed/local-dev.sql` remotely (no code path does; grep the script).
- Generated credentials print once and appear in no tracked file (verify with `git diff` + grep for
  the printed values).
- Minted email/password accounts can log in through the real `POST /v1/auth/login` (P2.4) —
  demonstrated in the verify transcript.
- `bun run test && bun run typecheck` green.

## Verify
```bash
cd apps/api && bun run test && bun run typecheck
cd apps/api && bun run db:migrate:local
bun run mint:account -- --state fresh --target local          # adjust to landed script name
bun run mint:account -- --state username-set --target local
bun run mint:account -- --state complete --with-goal --target local
cd apps/api && bun run dev
# with printed credentials from a mint above:
curl -s http://127.0.0.1:8787/v1/me -H "Authorization: Bearer <printed-token>"
```
Record in `_LEDGER.md`: the three mint transcripts (credentials redacted), each self-check result,
and the login round-trip evidence.

## Watch out
- If P1.4's landed tooling has no reusable remote-execution seam, or P2.4's login contract rejects
  generated credentials for a reason the packet didn't anticipate, mark blocked with the landed code
  cited — do not fork a second remote path.
- State minting must produce states that are REACHABLE through the real API (P3.3's transitions); if
  a flag would require writing a row combination the endpoints can never produce, that flag is wrong
  — fix the flag, not the database.
- Never print or embed `dev-alice-token` in preview contexts; it is a known development token
  (locked decision 16).
- `local-dev.sql` is consumed by existing iOS live tests — if you touch it, keep
  `usr_dev_alice`/`dev-alice-token` semantics identical and rerun the iOS suite before claiming
  done.
- No new markdown docs; usage lives in the script header.
