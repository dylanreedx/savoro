## Goal
Create `apps/api/src/lib/passwords.ts`: PBKDF2 hashing via WebCrypto with versioned parameters and a constant-time verify, fully unit-tested.

## Context and design direction
Read `_DESIGN.md` and `_RUNBOOK.md` before editing. No password code exists anywhere in `apps/api/src/` today; the only credential hashing in the repo is the SHA-256 session-token digest in `src/token.ts`, which is deliberately NOT a password hash and must not be reused for this. `src/lib/` currently holds only `apple.ts`. The credential columns landed in P2.1 (nullable hash/salt/params on `users`). This module is pure — no DB, no Hono — so P2.3/P2.4 can consume it cleanly. This ticket is deliberately scoped so another fresh agent can verify and land it independently.

## Approach
1. Implement `hashPassword(plaintext: string)`: generate a random ≥16-byte salt (`crypto.getRandomValues`), derive with `crypto.subtle.importKey('raw', …, 'PBKDF2', …)` + `deriveBits` using SHA-256, ≥600k iterations (OWASP 2023 floor for PBKDF2-HMAC-SHA256), 32-byte output. Return the stored representation per the approved P0.5 contract shape from P2.1 (separate hash/salt/params fields or one encoded string — match what P2.1 landed in `schema.ts`).
2. Encode params WITH the hash, versioned — e.g. params field `v1:pbkdf2-sha256:600000:32` — so future cost increases decode old rows. Export the current version constant; `verify` must dispatch on the stored version, never on the current default.
3. Implement `verifyPassword(plaintext, stored)`: decode stored params/salt, re-derive with the STORED parameters, compare digests in constant time. Workers exposes non-standard `crypto.subtle.timingSafeEqual`; use it, with a documented same-length XOR fold as the fallback if typechecking against `@cloudflare/workers-types` rejects it. Never `===` on the derived strings.
4. Tests (`test/passwords.test.ts`, vitest workers pool like the rest of `test/`):
   - hash-at-rest never equals or contains the plaintext; two hashes of the same password differ (random salt);
   - verify accepts the correct password and rejects a wrong one (name this test precisely, e.g. `'verifyPassword accepts the correct password'` — it is the negative-witness target);
   - params version upgrade path: construct a stored value with explicit v1 params at a non-default iteration count, confirm verify decodes and accepts it even if the module's default params differ;
   - malformed/unknown-version stored values reject (return false or throw per your API — pick one and test it), never crash into acceptance.

### Implementation sketch
```ts
// src/lib/passwords.ts (shape, not final code)
export const CURRENT_PARAMS = { version: 'v1', algo: 'pbkdf2-sha256', iterations: 600_000, keyLen: 32 }

export async function hashPassword(plaintext: string): Promise<StoredCredential> {
  const salt = crypto.getRandomValues(new Uint8Array(16))
  const bits = await derive(plaintext, salt, CURRENT_PARAMS)   // importKey + deriveBits
  return { hash: hex(bits), salt: hex(salt), params: encodeParams(CURRENT_PARAMS) }
}

export async function verifyPassword(plaintext: string, stored: StoredCredential): Promise<boolean> {
  const params = decodeParams(stored.params)          // stored version wins, not CURRENT_PARAMS
  if (!params) return false                           // unknown version never accepts
  const bits = await derive(plaintext, unhex(stored.salt), params)
  return timingSafeEqualHex(hex(bits), stored.hash)   // constant-time, never ===
}
```

## Watch out
- Do not reuse `hashToken` (`src/token.ts`) or plain SHA-256 for passwords — single-round digests are the exact failure PBKDF2 exists to prevent.
- Iteration count trade-off: Workers CPU limits are real; if 600k iterations makes the test suite or a request unacceptably slow, document the measured timing and pick the highest count that fits, in the versioned params — never silently lower it later.
- `Math.random` is forbidden for salts; `crypto.getRandomValues` only.
- Keep the module free of D1/Hono imports; if you find yourself importing `db/client`, the seam is wrong.
- If P2.1 landed a different stored shape (single encoded string vs three columns) or P0.8's contract names different params, follow the landed code/contract and note the delta; if P2.1 has not landed, mark blocked — the stored shape is its output.
